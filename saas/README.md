# Hookah POS SaaS — фундамент, онбординг, биллинг и APK-конвейер

Эта папка — НЕ часть одно-арендного приложения в корне репозитория (то,
что обслуживает ваше живое заведение, продолжает работать без изменений
в проекте `hoocah-pos`). Здесь строится ОТДЕЛЬНАЯ SaaS-платформа для
множества независимых заведений, разворачиваемая в НОВОМ Firebase-проекте.

## Что уже сделано (Phase 1)

- **Модель данных**: `tenants/{tenantId}`, `tenantMembers/{tenantId_uid}`,
  `users/{uid}`, `superAdmins/{uid}`, плюс все рабочие коллекции заведения
  вложены под `tenants/{tenantId}/...` (столы, чеки, меню, гости, склад,
  брони и т.д. — полный список см. в `firestore.rules`).
- **Firestore Security Rules** (`firestore.rules`) — полная изоляция
  арендаторов: сотрудник/гость одного заведения не может прочитать или
  изменить данные другого, даже зная его `tenantId` и будучи авторизованным
  в том же проекте платформы. Роли `owner/admin/manager/employee` реально
  проверяются на уровне правил (не только в интерфейсе).
- **Автоматические security-тесты** (`test/firestore.rules.test.js`) —
  проверяют именно это: Tenant A → A разрешено, Tenant A → B запрещено, для
  сотрудников всех ролей и для гостей, плюс что tenant/членство нельзя
  создать в обход бэкенда. **26 тестов, все проходят** — запускались через
  реальный Firestore-эмулятор при подготовке этой фазы, а не только
  написаны на бумаге.
- **Cloud Functions** (`functions/index.js`): `createTenant` (единственный
  способ завести заведение — клиент не может создать `tenants/{id}`
  напрямую), `resolveTenantBySlug` (публичный branding по коду заведения),
  `enableTenant`/`disableTenant` (супер-админ), `calculateUsage`
  (ежедневный подсчёт usage для будущего Super Admin дашборда).
  `handleBillingWebhook` и `createBuildJob` — честные заготовки: провайдер
  биллинга не выбран, а API GitHub Actions для сборки APK не подключён, они
  явно и осмысленно отказывают вместо того, чтобы притворяться рабочими.
- **Storage Rules** (`storage.rules`) — брендинг/меню публичны на чтение,
  экспорты/сборки APK — только владельцу/админу заведения.
- **Dart-модели и сервис** (`lib/models/tenant_models.dart`,
  `lib/services/tenant_config_service.dart`) — `Tenant`, `TenantMember`,
  роли с иерархией, настройки длительности кальяна на заведение (замена
  хардкода 90 минут), брендинг, feature-флаги с приоритетом
  platform→plan→tenant, статус подписки, локальный кэш конфигурации с
  офлайн-грейс-периодом. **Пока не подключены к работающему приложению** —
  это отдельный шаг следующей фазы (см. "Что дальше").
- **Юнит-тесты** на всю эту логику — `test/logic_test.dart`, группы
  `SaaS: *` (20 тестов: статусы, роли, лимиты тарифов, приоритет
  feature-флагов, round-trip кэша).
- **Миграция** (`migrations/migrate-single-tenant-to-tenant.js`) — скрипт
  переноса данных вашего текущего живого заведения в SaaS-проект как
  первого арендатора, когда вы будете готовы (см. ниже — намеренно НЕ
  запускается автоматически).

## Что сделано в Phase 2 (подключение приложения + консоль владельца)

- **`kSaasMode`** (`lib/build_info.dart`) — компиляционный флаг
  (`--dart-define=SAAS_MODE=true`). `.github/workflows/build-apk.yml` его не
  передаёт — существующая сборка ведёт себя байт-в-байт как раньше.
- **Весь доступ к Firestore переведён на `AppScope`**
  (`lib/services/app_scope.dart`) — ~230 мест в 34 файлах. Пока `AppScope`
  не переключён (`isSaasMode == false`, значение по умолчанию), пути к
  документам ровно те же, что были — это гарантированно, а не "должно
  быть", см. `scopedPath()` и юнит-тесты на неё.
- **Присоединение планшета к заведению** (`lib/screens/saas/
  saas_device_pairing_screen.dart`, `lib/services/
  saas_device_join_service.dart`) — по коду заведения (slug) + коду
  приглашения устройства, аналог `StaffDeviceSetupScreen` из одно-арендной
  версии, но в масштабе платформы: у каждого заведения свой код, а не один
  секрет на всех клиентов.
- **`main.dart`** в `kSaasMode` при старте проверяет членство устройства,
  и либо входит в заведение (`AppScope.enterTenant`, применяет
  `AppTheme.branded`, запускает фоновые службы), либо показывает экран
  присоединения. Обычная (не-SaaS) сборка не изменилась.
- **Runtime-брендинг** (`lib/theme/app_theme.dart`, `AppTheme.branded`) —
  фирменный основной цвет заведения накладывается на кнопки/акценты поверх
  базовой тёмной темы. Полная палитра/лого — задача следующего этапа.
- **Веб-консоль владельца** (`saas/console/`) — отдельный сайт на этом же
  Firebase-хостинге (`saas/firebase.json`, `public: console`), тот же
  рукописный стиль без сборки, что у гостевого `public/app`. Даёт
  владельцу: регистрацию/вход по email и паролю, создание заведения
  (вызывает `createTenant`), просмотр и обновление кода приглашения
  устройств, редактирование фирменного цвета, статус подписки. Это первый
  реальный клиент для Cloud Functions платформы — до него `createTenant`
  был вызываем только вручную (см. `Что дальше` в Phase 1).
- **Команда заведения из консоли**: список участников (владелец,
  приглашённые администраторы/менеджеры/сотрудники, самостоятельно
  присоединившиеся планшеты), приглашение нового человека по email
  (новая Cloud Function `inviteTenantMember` — ищет уже зарегистрированного
  в консоли пользователя через Admin SDK, клиент не может сделать это сам),
  смена роли manager/employee и включение/отключение доступа — всё через
  уже существующие правила `tenantMembers` (роль `owner`/`admin` через
  клиент по-прежнему недостижима, только вручную/через отдельную функцию
  в будущем — намеренное ограничение, см. правила).
- **Панель платформы (Super Admin)** — та же консоль (`saas/console/`),
  скрытая вкладка `#/admin`, видна только тому, у кого есть документ
  `superAdmins/{uid}` (см. шаг 3 ниже). Список всех заведений с usage
  (сотрудники/устройства/столы/гости — считает `calculateUsage`),
  блокировка/разблокировка заведения (`disableTenant`/`enableTenant`,
  уже существовали, но были без интерфейса). Потребовалось закрыть
  реальную дыру в правилах: `tenants/{tenantId}/usage/{doc}` до этого не
  имел ПОДХОДЯЩЕГО ПРАВИЛА ВООБЩЕ (Firestore по умолчанию запрещает,
  когда ни одно `match` не подошло) — `calculateUsage` писала данные,
  которые не мог прочитать вообще никто, включая супер-админа. Добавлено
  правило + 5 регрессионных тестов (`saas/test/firestore.rules.test.js`,
  группа "Usage-счётчики"). **Полный набор — 31/31 проходит.**

## Что сделано: биллинг (ЮKassa) и APK-конвейер (GitHub Actions)

- **`createCheckoutSession`** (Cloud Function) — создаёт платёж ЮKassa
  (`save_payment_method: true`, редирект на форму оплаты) для тарифа с
  `priceRub > 0`. Enterprise (`priceRub: 0`) через это не продаётся —
  честно отказывает с просьбой связаться с поддержкой (индивидуальные
  условия, не самообслуживание).
- **`handleBillingWebhook`** переписан из `onCall`-заглушки в настоящий
  `onRequest`-эндпойнт (ЮKassa шлёт обычный POST, не вызов через Firebase
  SDK). ЮKassa НЕ подписывает уведомления секретом (в отличие от Stripe) —
  их официально рекомендованная защита именно так и работает: по id
  платежа перезапросить его напрямую в API ЮKassa своим секретным ключом и
  доверять только тому, что вернул API, а не телу POST-запроса. Идемпотентно
  (`billingEvents/{paymentId}`) — повторная доставка не применяет оплату
  дважды. При `succeeded` — активирует подписку и заведение, сохраняет
  `paymentMethodId` (если ЮKassa подтвердила сохранение способа оплаты).
- **`chargeRecurringSubscriptions`** (раз в сутки) — автоматически списывает
  сохранённый способ оплаты за день до конца периода. Источник истины
  "оплачено" один — тот же webhook: этот шаг только инициирует платёж, а
  не меняет статус подписки сам (кроме перевода в `past_due` при явном
  отказе списания).
- **`createBuildJob`** — теперь по-настоящему запускает GitHub Actions
  (`workflow_dispatch` REST API, `.github/workflows/saas-on-demand-build.yml`)
  токеном из Secret Manager (`GITHUB_PAT`, права только `Actions: read/write`
  на этот репозиторий).
- **`completeBuildJob`** (новый `onRequest`-эндпойнт) — обратный вызов от
  GitHub Actions по завершении сборки (успех/ошибка), защищён общим
  секретом в заголовке (`BUILD_CALLBACK_SECRET`), а не Firebase Auth: раннер
  GitHub Actions не является клиентом Firebase.
- **`.github/workflows/saas-on-demand-build.yml`** (новый, отдельный от
  `build-apk.yml`) — собирает ОДИН универсальный APK кассы
  (`--dart-define=SAAS_MODE=true`) для ВСЕХ арендаторов сразу: конкретное
  заведение выбирается не на этапе сборки, а при первом запуске на планшете
  (`SaasDevicePairingScreen`). Кладёт результат в Firebase Storage SaaS-
  проекта (`tenants/{tenantId}/builds/{jobId}.apk` — путь уже был
  предусмотрен в `saas/storage.rules` с Phase 1). Файл специально НЕ
  объединён с `build-apk.yml` через матрицу/общий composite action и
  частично дублирует его шаги — `build-apk.yml` собирает боевые
  одно-арендные APK текущего живого заведения, трогать его ради SaaS-
  варианта означало бы риск сломать реальный, годами обкатанный пайплайн
  ради фичи, которая с ним не связана.
- **`lib/firebase_options.dart`** — теперь умеет собираться против ДВУХ
  разных Firebase-проектов: обычная сборка (`hoocah-pos`, как раньше,
  константы в коде) и `kSaasMode`-сборка (SaaS-проект платформы, ключи —
  через `--dart-define`, передаются в CI, не хранятся в репозитории рядом
  с продовым проектом).
- **Firestore**: новая коллекция `billingEvents` (идемпотентность webhook'а,
  видна только супер-админу) + правило для `usage`, найденное по пути (см.
  выше). Composite-индекс для `chargeRecurringSubscriptions`
  (`subscriptions`: `status`+`provider`+`currentPeriodEnd`). **3 новых
  security-теста, полный набор — 34/34.**
- **Консоль**: карточка «Подписка» теперь показывает реальные тарифы с
  ценой и кнопкой «Оформить» (редирект на форму оплаты ЮKassa), карточка
  «Сборка APK» — кнопка запуска сборки и список прошлых попыток со
  статусом и ссылкой на скачивание (через Firebase Storage SDK,
  `getDownloadURL`, доступ так же ограничен правилами — owner/admin этого
  заведения).

### Честные ограничения этой версии биллинга/конвейера

- **Автоплатежи (списание сохранённой карты) не включены "из коробки" на
  каждом магазине ЮKassa** — это отдельный продукт, включается по заявке в
  поддержку ЮKassa после подключения магазина. Без него `save_payment_method`
  всё равно работает для первого платежа, но `chargeRecurringSubscriptions`
  не сможет продлевать автоматически, пока продукт не подключён.
- **Не обработан статус `pending`** (требует 3-D Secure) у рекуррентного
  платежа — по соглашению с ЮKassa для сохранённого способа оплаты обычно
  настраивается его отсутствие, но это не проверено на реальном магазине.
  Полная дожимка платежей (ретраи, dunning-письма) — Phase 7 "production
  hardening" по ТЗ.
- **Один универсальный APK, не белый лейбл** — свой значок/имя приложения/
  applicationId под конкретное заведение всё ещё не реализованы (см.
  «Полный визуальный брендинг» ниже) — это отдельная, гораздо большая
  задача (Google Play не позволяет просто менять appId у уже
  опубликованного приложения, а один и тот же appId у разных заведений на
  одном устройстве конфликтует).
- **workflow_dispatch сработает только после того, как
  `saas-on-demand-build.yml` появится в ветке `main`** — GitHub требует,
  чтобы файл workflow'а существовал на том ref, который вы дёргаете
  (`ref: "main"` в `createBuildJob`).
- **Кастомные домены/поддомены** — не реализованы (Phase 3, TOR §27).
- **Ни один реальный SaaS-проект ещё не проходил весь путь целиком** —
  создание проекта → деплой → первое заведение → первая оплата → первая
  сборка APK → присоединение планшета ни разу не прогонялось руками на
  настоящем Blaze-проекте (только автоматические security-тесты на
  эмуляторе и юнит-тесты Dart-логики). Прежде чем продавать первому
  клиенту, стоит один раз пройти этот путь целиком самостоятельно.

## Что сделано: полная палитра брендинга и доводка Super Admin

- **`AppTheme.branded`** теперь применяет ВСЮ палитру заведения, а не
  только основной цвет: фон (`scaffoldBackgroundColor`), цвет текста
  (`textTheme`, `appBarTheme`, `iconTheme`), вторичный цвет
  (`colorScheme.secondary`) и отдельный цвет кнопок (`buttonColor`,
  независимо от primary — некоторым брендам нужен другой акцент для CTA).
  Пара фон/текст проверяется на контраст по формуле WCAG (порог 3:1, как
  для крупного текста) — при недостаточном контрасте ЭТА ПАРА откатывается
  на цвета темы по умолчанию, а не применяется вслепую: интерфейс на
  планшете в тёмном зале не должен становиться нечитаемым только потому,
  что владелец ввёл цвета не глядя на реальный экран.
- **Исправлен реальный разнобой палитры по умолчанию**: значения по
  умолчанию `BrandingConfig` (и то, что `createTenant` заводит новому
  заведению) были скопированы из палитры ГОСТЕВОГО веб-приложения
  (`public/app/app.css`, зелёно-бирюзовая), а не из настоящей палитры
  POS-приложения "Midnight Blue" (`lib/theme/app_colors.dart`, сине-чёрная).
  Из-за этого новое SaaS-заведение БЕЗ кастомного брендинга выглядело бы
  иначе, чем проверенный одно-арендный продукт — не потому что владелец
  что-то настроил, а по ошибке в дефолтах. Исправлено в трёх местах
  одновременно (`lib/models/tenant_models.dart`,
  `saas/functions/index.js`, `saas/console/console.js`), чтобы не
  разъехались снова.
- **`AppScope.branding`** — новое статическое поле (вместе с `tenantId`),
  чтобы экраны, которые НЕ читают `Theme.of(context)` для своих цветов
  (например `LoginScreen` — исторически рисует всё литеральными
  `Color(...)`, в обход темы), всё равно могли показать имя и логотип
  заведения. Экран входа персонала теперь показывает `branding.appName` и
  `branding.logoUrl` вместо жёстко зашитого «Hookah POS» — именно то место,
  которое ТЗ называет «имя приложения на экране входа» (§17/§18).
- **Консоль**: карточка «Брендинг» — имя приложения, логотип (загрузка в
  Firebase Storage, `tenants/{tenantId}/branding/`, путь уже был разрешён
  правилами с Phase 1), 5 цветовых пикеров (основной/вторичный/кнопки/
  фон/текст) и живой мини-предпросмотр с тем же расчётом контраста, что и
  в приложении (предупреждает ДО сохранения, а не после). Форма не
  сбрасывает не сохранённые правки при фоновых обновлениях экрана
  (статус сборки APK и т.п. больше не затирают то, что владелец ещё не
  сохранил).
- **Панель Super Admin**: поиск по названию/коду заведения (фильтрует уже
  загруженный список — простое и рабочее решение, пока заведений не
  тысячи), ручная смена тарифа заведению (новая Cloud Function
  `changeTenantPlan`, только для супер-админа — для владельца остаётся
  `createCheckoutSession`), лента последних 50 записей платформенного
  `auditLogs` (кто что сделал и когда).

## Что сделано: льготный период и реальное удаление данных за неуплату

Раньше просроченная подписка (`past_due`) не вела никуда — заведение
годами могло висеть в этом статусе, ничего не платя, а данные оставались
навсегда. Теперь у неоплаты есть настоящий конец:

- **`GRACE_PERIOD_DAYS = 10`** (`saas/functions/index.js`) — с момента, как
  подписка стала `past_due` (`pastDueSince`), у владельца есть 10 дней
  продлить её, прежде чем данные удалятся. **Жёсткая блокировка** (не
  "мягкая", как в более ранней версии этой документации): касса и
  приложение полностью недоступны с первой же минуты просрочки —
  `TenantStatus.pastDue.allowsOperations` теперь `false`, а не `true`
  (см. `lib/models/tenant_models.dart`). 10 дней — это только отсрочка
  перед удалением данных, а не период, в который можно продолжать
  работать неоплаченным.
- **`enforceGracePeriod`** (новая Cloud Function, раз в сутки) закрывает
  ВСЕ пути, которыми подписка могла зависнуть, не продлеваясь и не
  теряя доступ:
  1. Триал закончился, а оплата так и не прошла (`chargeRecurringSubscriptions`
     не видит триальные подписки вообще — у них ещё нет `provider`) —
     включает тот же 10-дневный отсчёт.
  2. Оплаченный период закончился, а подписка всё ещё `active` (нечем было
     списать автоматически, или списание просто не случилось) — то же
     самое: раньше такая подписка осталась бы `active` НАВСЕГДА.
  3. Просрочка тянется дольше 10 дней — **данные заведения реально
     стираются** (`purgeTenantData`): все вложенные коллекции (столы, чеки,
     меню, гости, склад, сотрудники, устройства, настройки, брендинг —
     полный список см. `TENANT_SUBCOLLECTIONS` в коде, он идентичен
     перечню коллекций в `firestore.rules`) удаляются рекурсивно
     (`db.recursiveDelete`, включая вложенные подколлекции вроде
     `clients/{id}/visits`), участники (`tenantMembers`) удаляются. Сам
     документ `tenants/{tenantId}` НЕ удаляется — помечается `status:
     "deleted"` (код заведения не освобождается для повторного
     использования, в `auditLogs` остаётся, что заведение существовало).
     Подписка помечается `cancelled`. Вернуться после этого можно только
     заново пройдя онбординг — ровно то, что и просили: «нужно всё заново
     настраивать».
- **Консоль**: если подписка `past_due`, владелец видит красную карточку
  с обратным отсчётом («данные будут удалены через N дней») прямо над
  карточкой подписки, кнопки продления становятся основными (не блёклыми).
  Панель Super Admin показывает то же предупреждение на карточке
  заведения — оператор платформы видит, кому вот-вот сотрут данные, не
  открывая каждое заведение по отдельности.
- **Dart**: `SubscriptionInfo.pastDueSince` + `daysUntilDataPurge()` — то
  же вычисление, что и в консоли (`saas/console/console.js`,
  `daysUntilDataPurge()`) и в Cloud Function, продублировано намеренно
  (три разных рантайма) и задокументировано в каждом месте.
- **Реально проверено** (не только написано): против настоящего Firestore-
  эмулятора — заведение с данными в нескольких коллекциях, включая
  вложенную `clients/{id}/visits`, было заведено и прогнано через
  `purgeTenantData` целиком; отдельно проверена выборка трёх новых
  запросов (`enforceGracePeriod`) на семи специально расставленных
  подписках (просроченный триал / ещё живой триал / просроченная активная
  без недавней попытки списания / просроченная активная С недавней
  попыткой — не должна попасть под раздачу / активная с запасом /
  просрочка старше 10 дней / просрочка моложе 10 дней) — каждый запрос
  отобрал ровно ожидаемые документы, ни одного лишнего или пропущенного.
  Новые 3 составных индекса — в `saas/firestore.indexes.json`.

### Честные ограничения

- **Нет автоматического email/push-уведомления владельцу** о начале
  отсчёта или о приближении дедлайна — предупреждение видно, только если
  зайти в консоль. Реальное уведомление (почта/телеграм) — отдельная
  задача, нужен email-провайдер (та же категория решений, что и биллинг).
- **Устройство, работающее в момент удаления**, не получает вежливого
  предупреждения — оно просто начнёт получать `permission-denied` на
  следующей операции с базой (`tenantMembers` этого устройства тоже
  удалён). Экраны в основном уже проглатывают такие ошибки молча
  (устоявшийся в проекте паттерн `onSnapshot(..., () => {})`), но
  отдельного "ваше заведение только что удалено, перезапустите" диалога
  нет.
- **Нет ручной кнопки «продлить прямо сейчас без ожидания webhook'а»** для
  супер-админа — если оплата вручную (не через ЮKassa), продлить подписку
  и снять `past_due` можно только напрямую через консоль Firestore
  (обновить `subscriptions/{tenantId}.status` на `active` и
  `currentPeriodEnd`), интерфейса для этого в консоли пока нет.

## Что сделано: жёсткая блокировка кассы, разная длина PIN, тарифы и аналитика

**Жёсткая блокировка (по прямому запросу — не "мягкая", как раньше).**
`TenantStatus.pastDue.allowsOperations` теперь `false` (было `true`).
Раньше просроченное заведение продолжало нормально работать все 10 дней
льготного периода — теперь касса и приложение блокируются с первой же
минуты просрочки, а 10 дней остаются только отсрочкой перед удалением
данных, не рабочим временем.

- **`lib/services/subscription_gate.dart`** (новый) — живой сторож:
  слушает `tenants/{tenantId}` и `subscriptions/{tenantId}` в реальном
  времени ВСЁ время работы приложения, а не только на старте. Без этого
  просрочка, наступившая посреди смены, ничего не меняла бы до следующего
  перезапуска планшета — `TenantConfigService.refresh()` вызывается только
  один раз при запуске.
- **`lib/screens/saas/saas_subscription_blocked_screen.dart`** (новый) —
  экран блокировки: имя заведения, объяснение, обратный отсчёт дней до
  удаления данных (`SubscriptionInfo.daysUntilDataPurge`), кнопка
  "Проверить снова". Показывается через `MaterialApp.builder` в
  `main.dart` — это значит, что он перекрывает ЛЮБОЙ текущий экран
  приложения, а не только точку входа, то есть сработает, даже если
  просрочка наступила прямо посреди работы кассира.
- Кэш конфигурации (`TenantConfigService`, офлайн-режим) научился
  сохранять `trialEndsAt`/`currentPeriodEnd`/`pastDueSince` — без этого
  восстановленный из кэша (офлайн) конфиг не смог бы посчитать обратный
  отсчёт на экране блокировки.

**Разная длина PIN у ролей.** Сотрудник — 4 цифры (как раньше), администратор
— 6 (`lib/utils/constants.dart`, `AppConstants.pinLengthForRole`). Экран
входа (`lib/screens/login_screen.dart`) получил явный переключатель
"Сотрудник / Администратор" над клавиатурой — намеренно явный, не
автоопределение по факту совпадения кода: в момент ввода ещё не известно,
сколько цифр ждать, чтобы автовход сработал сразу после последней. Форма
добавления/редактирования сотрудника (`lib/screens/admin/employees_screen.dart`)
проверяет длину PIN по выбранной роли. **Обратная совместимость**: уже
существующие сотрудники с ролью admin и старым 4-значным PIN продолжают
входить как раньше — проверка длины применяется только при создании/
редактировании записи, ничего не переписывает существующие данные
принудительно.

**Тарифы и аналитика в панели Super Admin** (`saas/console/console.js`,
`#/admin`):
- **Тарифы** — полноценный редактор прямо в консоли: название, цена,
  лимиты (сотрудники/устройства/столы/хранилище, 0 = без лимита),
  ИИ/брендинг/домен — и кнопка "Добавить тариф" для нового. Работает
  прямой записью в Firestore (`plans/{planId}`), без отдельной Cloud
  Function — правила и так разрешают супер-админу запись без ограничений
  (`saas/firestore.rules`), это подтверждено новым security-тестом.
  Тонкости per-feature флагов (`features.reservations` и т.п.) в форму не
  вынесены — редактируются напрямую в Firestore-консоли при необходимости.
- **Аналитика** — плитки: всего заведений, активных подписок, MRR (оценка
  — сумма цены тарифа по всем `active`-подпискам), выручка (сумма
  `amount` из последних 500 обработанных платежей ЮKassa —
  `billingEvents`, поле `amount` добавлено в `handleBillingWebhook`
  специально для этого), регистрации за 7/30 дней, разбивка заведений по
  статусам. Всё считается на клиенте из уже загруженных данных — без
  отдельных агрегирующих Cloud Functions: честно масштабируется на
  сотни-первые тысячи заведений и платежей, не на миллионы (та же
  оговорка, что и у `limit(200)`/`limit(500)` в остальной части панели).

## Настройка нового SaaS-проекта

### 1. Создать Firebase-проект

Через [Firebase Console](https://console.firebase.google.com/) или CLI:

```bash
firebase projects:create <ваш-saas-project-id>
```

**Включите тариф Blaze** — Cloud Functions (scheduler, secrets, вызов
внешних API для биллинга/GitHub) недоступны на бесплатном Spark. Это
осознанное решение, принятое отдельно от бесплатного тарифа
одно-арендного проекта — see корневой README, раздел «Работа на
бесплатном тарифе Firebase (Spark)», который по-прежнему актуален для
вашего текущего заведения и никак не меняется этим переходом.

Впишите id проекта в `saas/.firebaserc` вместо
`REPLACE_WITH_YOUR_NEW_SAAS_PROJECT_ID`.

Включите в консоли: **Firestore Database**, **Authentication → Email/
Password** (владельцы заведений входят по-настоящему, не анонимно — в
отличие от гостей и планшетов, которые остаются анонимными), **Storage**.

### 2. Развернуть правила, индексы и функции

```bash
cd saas
firebase deploy --project <ваш-saas-project-id>
```

(из `saas/firebase.json` — деплоит firestore rules+indexes, storage rules
и functions за один раз).

### 3. Завести первого супер-администратора

Вручную в консоли Firestore нового проекта — коллекция `superAdmins`,
документ с id, равным вашему будущему Firebase Auth uid (создайте себе
аккаунт email/password в Authentication, скопируйте uid оттуда):

```json
{ "since": "2026-01-01T00:00:00Z" }
```

Это не автоматизируется намеренно — как и `staffSecret` в одно-арендной
версии, первый вход с правами платформы не может выдаваться самим
приложением.

### 4. Загрузить тарифы

```bash
cd saas/scripts && npm i
node seed-plans.js --project <ваш-saas-project-id> --key ./service-account.json
```

(файл `service-account.json` — из Firebase Console → Project settings →
Service accounts → Generate new private key; не коммитить в git).

### 5. Создать первое (тестовое) заведение — через веб-консоль

```bash
firebase deploy --only hosting --project <ваш-saas-project-id>
```

Откройте `https://<ваш-saas-project-id>.web.app`, зарегистрируйтесь по
email/паролю (кнопка «Зарегистрироваться»), заполните название и код
заведения — консоль вызовет `createTenant` сама и покажет код
приглашения устройства. Локально, без деплоя, можно проверить то же самое
через `firebase emulators:start` (см. `saas/firebase.json` — хостинг
эмулятора уже настроен на порт 5000) — но тогда `/__/firebase/init.json`
эмулятор не отдаёт настоящие ключи проекта, поэтому для реальной проверки
удобнее один раз задеплоить хостинг и открыть боевой адрес.

Полученный код заведения (slug) и код приглашения устройства и есть то,
что вводится в `SaasDevicePairingScreen` на планшете при первом запуске
SaaS-сборки приложения (`--dart-define=SAAS_MODE=true`).

### 6. Запустить тесты изоляции арендаторов самостоятельно

```bash
cd saas/test && npm i
cd .. && npx firebase-tools emulators:exec --project hookah-saas-rules-test \
  --only firestore "cd test && npm test"
```

Ожидаемый результат: все тесты проходят (на момент написания — 45/45).
Любое изменение `firestore.rules` в будущем должно повторно проходить
этот набор ДО деплоя в реальный проект — именно так был пойман и исправлен
реальный баг при подготовке Phase 1 (общий catch-all правил тихо
перекрывал более узкие ограничения по ролям — см. комментарий в конце
`firestore.rules`) и дыра в правилах Phase 2 (`usage` не имел вообще
никакого правила — см. "Что сделано в Phase 2" выше).

### 7. Настроить биллинг (ЮKassa)

1. Заведите магазин на [yookassa.ru](https://yookassa.ru/) (если ещё нет) —
   получите `shopId` и секретный ключ (Личный кабинет → Настройки →
   API-ключи).
2. Секреты — в Secret Manager ВАШЕГО SaaS-проекта, не в `.env` и не в git:
   ```bash
   firebase functions:secrets:set YOOKASSA_SHOP_ID --project <ваш-saas-project-id>
   firebase functions:secrets:set YOOKASSA_SECRET_KEY --project <ваш-saas-project-id>
   ```
3. Разверните функции (`firebase deploy --only functions --project ...`) —
   после деплоя скопируйте боевой URL функции `handleBillingWebhook` (в
   выводе `firebase deploy` или `firebase functions:list`; для 2-го
   поколения функций это отдельный `*.a.run.app`-адрес, не
   `<region>-<project>.cloudfunctions.net/...`).
4. В личном кабинете ЮKassa: Настройки → HTTP-уведомления — впишите туда
   этот URL и включите события `payment.succeeded` и `payment.canceled`.
5. **Автоплатежи** (списание сохранённой карты для продления без участия
   владельца) — отдельный продукт ЮKassa, включается по заявке в их
   поддержку ПОСЛЕ подключения магазина. Без него первый платёж по тарифу
   всё равно проходит, а `chargeRecurringSubscriptions` не сможет продлить
   автоматически, пока продукт не одобрен.
6. Проверьте: в консоли откройте заведение → «Подписка» → «Оформить» —
   должно перекинуть на настоящую форму оплаты ЮKassa (в тестовом режиме
   магазина — тестовыми картами из документации ЮKassa).

### 8. Настроить APK-конвейер (GitHub Actions)

1. Секреты Cloud Functions (Secret Manager SaaS-проекта):
   ```bash
   firebase functions:secrets:set GITHUB_PAT --project <ваш-saas-project-id>
   firebase functions:secrets:set BUILD_CALLBACK_SECRET --project <ваш-saas-project-id>
   ```
   `GITHUB_PAT` — fine-grained personal access token на GitHub (Settings →
   Developer settings → Personal access tokens → Fine-grained), доступ
   ТОЛЬКО к репозиторию `Ghosts1996/pos`, права ТОЛЬКО `Actions: Read and
   write`. `BUILD_CALLBACK_SECRET` — любая случайная строка, которую вы же
   придумываете (например `openssl rand -hex 32`) — она же пойдёт ниже в
   секреты репозитория GitHub, обе стороны должны знать одно и то же
   значение.
2. После `firebase deploy --only functions` скопируйте боевой URL функции
   `completeBuildJob` (аналогично `handleBillingWebhook` выше).
3. В GitHub-репозитории (Settings → Secrets and variables → Actions →
   New repository secret) заведите:
   - `GOOGLE_SERVICES_JSON_SAAS` — конфиг Android-приложения
     `com.hookahpossaas`, зарегистрированного в консоли ВАШЕГО SaaS
     Firebase-проекта (Project settings → Your apps → Add app → Android,
     package name ровно `com.hookahpossaas`), содержимое `google-services.json`.
   - `SAAS_FIREBASE_API_KEY`, `SAAS_FIREBASE_APP_ID`,
     `SAAS_FIREBASE_MESSAGING_SENDER_ID`, `SAAS_FIREBASE_PROJECT_ID`,
     `SAAS_FIREBASE_STORAGE_BUCKET` — те же значения, что в
     `google-services.json` выше/в консоли Firebase (Project settings →
     General): именно они попадают в приложение через `--dart-define` (см.
     `lib/firebase_options.dart`).
   - `SAAS_STORAGE_BUCKET` — имя бакета Storage (Project settings → General
     → Storage bucket, например `<project-id>.firebasestorage.app`).
   - `SAAS_STORAGE_SERVICE_ACCOUNT` — JSON-ключ сервисного аккаунта с
     ролью `Storage Object Admin` на этом бакете (Google Cloud Console →
     IAM → Service accounts → Create → скачать ключ; давайте ему доступ
     ТОЛЬКО к Storage, не ко всему проекту).
   - `SAAS_COMPLETE_BUILD_JOB_URL` — URL `completeBuildJob` из шага 2 выше,
     целиком (`https://...`), без добавления пути.
   - `BUILD_CALLBACK_SECRET` — то же значение, что в Secret Manager на шаге 1.
   - `ANDROID_KEYSTORE_BASE64`, `ANDROID_KEYSTORE_PASSWORD`,
     `ANDROID_KEY_ALIAS`, `ANDROID_KEY_PASSWORD` — если уже настроены для
     `build-apk.yml`, переиспользуются как есть (тот же издатель, тот же
     постоянный ключ подписи).
4. Убедитесь, что `.github/workflows/saas-on-demand-build.yml` уже в ветке
   `main` — GitHub допускает `workflow_dispatch` только для workflow-файла,
   присутствующего на том ref, на который дёргает `createBuildJob`
   (`ref: "main"`).
5. Проверьте: в консоли откройте заведение → «Сборка APK» → «Собрать APK».
   Через 5–10 минут в списке должна появиться запись «готова» со ссылкой
   «Скачать».

### 9. Перенос вашего текущего заведения (когда будете готовы)

**Не раньше, чем Phase 1–3 обкатаны на тестовых заведениях.** Тогда:

```bash
cd saas/migrations && npm i
node migrate-single-tenant-to-tenant.js \
  --source-project hoocah-pos --source-key ./hoocah-key.json \
  --target-project <ваш-saas-project-id> --target-key ./saas-key.json \
  --tenant-id <tenantId, уже созданный через createTenant>
```

Ничего не удаляет и не меняет в `hoocah-pos` — только читает оттуда и
пишет в новый проект. Ваше текущее заведение продолжает работать всё это
время без остановки.

## Что дальше (следующие чек-ины)

1. **Белый лейбл для APK**: свой значок/имя/applicationId под конкретное
   заведение вместо одного универсального APK на всех — понадобится для
   заведений, которые хотят публиковать свою версию в Google Play под
   своим именем (Enterprise-тариф, TOR — отдельная большая задача, отдельная
   регистрация Android-приложения в Firebase на каждое такое заведение).
2. **Настоящая курсорная пагинация Super Admin** — сейчас `limit(200)` +
   клиентский поиск по уже загруженному списку, достаточно на старте, но
   не масштабируется на тысячи заведений.
3. **Биллинг — дожимка**: обработка `pending`/3-D Secure у рекуррентных
   платежей, ретраи и dunning-письма при неудачном продлении, отмена
   подписки из консоли (сейчас можно только оформить, отменить — только
   вручную через Firestore/поддержку).
4. **Повышение до admin/второго owner** — сейчас клиентская запись
   `tenantMembers` ограничена ролями manager/employee (см.
   `inviteTenantMember`/правила), совладельцев по-прежнему можно добавить
   только вручную через консоль Firebase — нужна отдельная Cloud Function
   с проверкой лимита тарифа на число совладельцев.
5. **Кастомные домены/поддомены** (TOR §27) и полноценный перенос вашего
   текущего заведения (шаг 9 выше) — после того как всё это обкатано на
   тестовых заведениях, включая полный путь оплаты и сборки APK на
   реальном Blaze-проекте (см. «Честные ограничения» выше).
