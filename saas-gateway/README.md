# saas-gateway

Серверная часть платформы ZalPOS (проект Firebase `saas-3bdc8`) на том же
сервере, что и `pii-gateway/`. Здесь всё, что нельзя доверить клиенту и
нельзя держать в Cloud Functions без тарифа Blaze.

Что умеет (адреса — `POST /saas/<имя>`, если не сказано иное):

- **Заведения и сети:** `createTenant`, `createChain`, `convertTenantToChain`,
  `resolveTenantBySlug`, `resolveChainBySlug`, `inviteTenantMember`,
  `createDemoTenant` (демо удаляется само через несколько часов). После
  создания заведения или сети в фоне выпускается сертификат для
  `{slug}.zalpos.ru` (`provision-tenant-domain.sh`, см. `saas/README.md`,
  раздел 8c — там же про sudoers).
- **Сборки приложений:** `createBuildJob`, `completeBuildJob` (обратный вызов
  сборки), `rolloutApps` (автообновление всем), `getDownloadUrl`,
  `GET downloadBuild`, `GET publicGuestApk` (гостевой APK по QR, без входа),
  `appUpdate` (приложения сами проверяют новую версию).
- **Оплата:** `createCheckoutSession`, `robokassaResult` / `robokassaSuccess` /
  `robokassaFail` (они же принимают оплату гостей заведения), счета для ИП и
  организаций (`createBankInvoice`, `markBankInvoicePaid`,
  `markBankInvoiceReceipt`, `cancelBankInvoice`), `cancelSubscription` /
  `resumeSubscription`. Раз в сутки — автопродление и перевод в `past_due`
  с удалением данных после льготного периода.
- **Файлы заведения:** `uploadBrandingLogo`, `uploadMenuImage` — на диск
  сервера (`branding-uploads/`), читаются публично через nginx.
- **Панель платформы:** модерация (`enableTenant`, `disableTenant`,
  `changeTenantPlan`, `grantBonusPeriod`, `deleteDemoTenant`,
  `overrideSubscription`), тарифы (`savePlan`, `deletePlan`,
  `applyPlanCatalog` — рекомендованная сетка с предпросмотром), реквизиты
  (`savePlatformLegal`), безопасность (супер-админы, сеансы, блок-лист,
  устройства, резервные копии, сертификаты), запросы по персональным данным.
- **Гость:** `aiProxy` (ИИ-помощник без доступа гостя к ключам),
  `deleteGuestData`, `registerGuestRecovery` / `restoreGuestSession`.
- **Прочее:** `GET firebaseConfig` (публичный веб-конфиг для гостевого веба),
  `sendAuthEmail` (письма входа в оформлении ZalPOS), суточный пересчёт
  лимитов тарифа и хитов меню.

Все изменения подписок и тарифов из панели идут только через сервис и
пишутся в `securityLog` («было → стало»).

**Возможности тарифа.** Тариф решает, есть ли у заведения приложение гостя
с меню по QR (`features.guestApp`), ИИ-помощник (`aiEnabled`) и сколько в нём
сотрудников (`maxEmployees`, 0 — без лимита). Сервер переносит это в
заведение (`syncTenantCapabilities`): `tenants/{id}.guestAppOff` — по нему
правила базы пускают гостей, и публичный `tenants/{id}/public/features` —
его читают касса, приложение и веб гостя. Синхронизация — при создании
заведения, оплате, смене тарифа (`changeTenantPlan`, `changeTrialPlan` —
владелец сам в пробный период), правке тарифа и раз в сутки. У точки сети
возможности — по тарифу сети, демо — всё. Без приложения гостя «Собрать APK»
собирает только кассы, `aiProxy` отвечает 403.

**Сетка тарифов** (`PLAN_CATALOG` в server.js, она же `saas/plans.seed.json`):
«Старт» 1 790 ₽ (до 5 сотрудников, приложение гостя), «Бизнес» 2 390 ₽ (до 10,
приложение гостя и ИИ), «Про» 2 990 ₽ (без ограничений, приоритетная
поддержка — обращения таких заведений в панели помечены и стоят первыми),
«Сеть» 2 590 ₽ + 990 ₽ за следующую точку (до 10 сотрудников на точке),
«Сеть Про» 3 990 ₽ + 1 290 ₽.
Рабочие места (устройства) не ограничены ни в одном тарифе. Сетка
сама ничего не меняет: её применяет супер-админ кнопкой в панели, увидев
изменения. Подорожание для тех, кто уже платит, начинает действовать через
30 дней (как в оферте): прежние цены закрепляются в
`subscriptions.priceLock` и действуют на продление и доп. точки сети. IP клиента берётся из
`X-Real-IP` от nginx, без него в журнале будет 127.0.0.1.

Сервис работает только с проектом `saas-3bdc8`; база собственного
заведения владельца платформы (`hoocah-pos`) отсюда недоступна.

## Установка

```bash
cd saas-gateway
./setup.sh
```

Скрипт поставит Node.js 20 (если его ещё нет — на этом сервере он уже
должен быть, ставили для `pii-gateway`), скопирует сервис в
`/opt/saas-gateway`, спросит сервисный ключ Firebase, GitHub-токен и секрет
обратного вызова — и запустит всё как systemd-сервис (`saas-gateway`,
слушает `127.0.0.1:8081`).

По ходу скрипт попросит:
1. **Сервисный аккаунт Firebase проекта `saas-3bdc8`** (не `hoocah-pos`!) в
   base64. Получить: Firebase Console → проект `saas-3bdc8` → Project
   settings → Service accounts → Generate new private key → скачается
   JSON. Дальше как и с pii-gateway: вставить содержимое файла в
   `cat > /tmp/key.json`, затем `base64 -w0 /tmp/key.json`, вставить вывод
   в скрипт, потом `rm -f /tmp/key.json`.
2. **GitHub personal access token** (fine-grained,
   github.com/settings/tokens?type=beta) с правами ТОЛЬКО "Actions: read
   and write" на репозиторий `Ghosts1996/pos` — нужен, чтобы сервис мог
   сам запускать сборку APK.
3. **Секрет обратного вызова** (`BUILD_CALLBACK_SECRET`) — придумайте
   случайную строку (`openssl rand -hex 24`) и запомните: то же самое
   значение нужно прописать в GitHub как секрет репозитория с тем же
   именем (см. ниже).
4. **Публичный веб-конфиг Firebase** (`FIREBASE_WEB_CONFIG_JSON`) — НЕ
   секрет (те же ключи видны в исходнике любой веб-страницы с Firebase).
   Получить: Firebase Console → `saas-3bdc8` → Project settings → General
   → Your apps → веб-приложение (значок `</>`) → «SDK setup and
   configuration» → переключатель «Config» → скопировать объект целиком
   в одну строку. Нужен, чтобы `saas/guest-web/` на поддоменах
   `{slug}.zalpos.ru` мог инициализировать Firebase — см. `firebaseConfig`
   выше и докстринг `handleFirebaseWebConfig` в `server.js`.

**Если сервис уже установлен раньше** (обновляете существующий, а не
ставите с нуля) — `setup.sh` повторно не запускать, просто добавить
строки в уже существующий `/etc/saas-gateway.env`:

```bash
echo 'FIREBASE_WEB_CONFIG_JSON={"apiKey":"...","authDomain":"...",...}' >> /etc/saas-gateway.env
systemctl restart saas-gateway
```

**Обновление КОДА самого сервиса** (`server.js` и т.п. поменялся, а не
только переменные окружения) — `/opt/saas-gateway` не git-репозиторий сам
по себе (`setup.sh` копирует файлы туда один раз), поэтому `git pull`
внутри него ничего не даст. Обновляйте через уже склонированный где-то
репозиторий (например `/root/pos-deploy`, если делали это раньше для
консоли — см. `saas/README.md`):

```bash
cd /root/pos-deploy && git fetch origin production && git checkout production && git pull origin production
rsync -a --exclude node_modules /root/pos-deploy/saas-gateway/ /opt/saas-gateway/
cd /opt/saas-gateway && npm install --omit=dev
chown -R saas-gateway:saas-gateway /opt/saas-gateway
systemctl restart saas-gateway
```

`rsync -a` без `--delete` — существующие `tenant-builds/`/
`branding-uploads/` (реальные файлы сборок и логотипов на диске) при этом
не трогаются, обновляется только код.

## Автообновление приложений и место на диске

Владельцу не нужно нажимать «Собрать APK» после каждого обновления
платформы. Изменился код приложений (`lib/**`, `assets/**`, `pubspec.*`) —
workflow `.github/workflows/saas-rollout.yml` сообщает серверу коммит
(`POST /saas/rolloutApps`, тот же секрет `BUILD_CALLBACK_SECRET`, что у
`completeBuildJob`), и сервер сам по очереди, по два заведения
одновременно, пересобирает кассу (Android и Windows) и гостевое
приложение всем заведениям, у которых приложения уже собирались.
Приложения на устройствах находят новую версию, скачивают её в фоне и
показывают «Установить».

- Несколько push подряд склеиваются: сборка начинается через 5 минут после
  последнего. Коммит с `[no rollout]` в сообщении не раскатывается.
- Сборка какого-то заведения упала — раскатка встаёт на паузу (битую версию
  всем не собираем). Причина видна в панели платформы → «Сборки APK»;
  там же кнопка «Пересобрать приложения всем заведениям» — она же
  снимает паузу.
- Заведения без активной подписки пропускаются.

На диске (`/opt/saas-gateway/tenant-builds`) у каждого заведения хранится
только последняя сборка каждого приложения — три файла, примерно
80–100 МБ. Как только готова новая, старая помечается «заменена новой
версией» и её файл удаляется. Раз в сутки сервер дочищает всё лишнее
(файлы без записи о сборке, папки удалённых заведений) и удаляет записи
об ошибках и заменённых сборках старше 60 дней.

## Оплата через Робокассу

Подписки оплачиваются только через Робокассу (ЮKassa убрана). Для
самозанятого чек в «Мой налог» Робокасса формирует сама — чек из
платформы не передаётся.

**Робокасса → «Мои магазины» → магазин → «Технические настройки»:**

| Поле | Значение |
|---|---|
| Алгоритм расчёта хеша | `SHA256` (то же — в `ROBOKASSA_HASH`) |
| Result Url | `https://pii.zalpos.ru/saas/robokassaResult`, метод GET или POST |
| Success Url | `https://pii.zalpos.ru/saas/robokassaSuccess`, метод GET |
| Fail Url | `https://pii.zalpos.ru/saas/robokassaFail`, метод GET |

Адреса взаимозаменяемы с гостевыми (`guestPayRobokassa`, `guestPayDone`):
платёж гостя заведения узнаётся по `Shp_t`, подписка — по его отсутствию.
Поэтому один магазин может принимать и то и другое — но магазин
самозанятого для продаж заведения не годится: каждый платёж гостя
Робокасса зарегистрирует в «Мой налог» как доход самозанятого, а кафе или
кальянная с сотрудниками под НПД не подпадают (нельзя нанимать работников,
перепродавать товары и продавать подакцизное). Заведению — отдельный
магазин Робокассы на его ИП или ООО; чек по 54-ФЗ пробивает касса
заведения, «Робочеки» в таком магазине не включать.
| Пароль №1, Пароль №2 | придумать (разные) и вписать на сервер |

**Сервер** (`/etc/saas-gateway.env`, затем `systemctl restart saas-gateway`):

```bash
ROBOKASSA_LOGIN=ZalPOS            # идентификатор магазина
ROBOKASSA_PASSWORD1=...           # пароль №1
ROBOKASSA_PASSWORD2=...           # пароль №2
ROBOKASSA_HASH=sha256
ROBOKASSA_TEST=1                  # пока магазин не активирован: тестовые пароли и платежи
# ROBOKASSA_RECURRING=1           # когда Робокасса включит периодические платежи
```

- Пока магазин не активирован, платежи только тестовые: в `ROBOKASSA_TEST=1`
  режиме вписываются **тестовые** пароли из того же раздела. После
  активации — боевые пароли и строку `ROBOKASSA_TEST` убрать.
- Автопродление (`ROBOKASSA_RECURRING=1`) включать только после того, как
  поддержка Робокассы подключит магазину периодические платежи. Без него
  владелец оплачивает каждый период сам из личного кабинета. Даже с ним
  автосписания идут только у тех, кто при оплате поставил галочку
  «Автопродление» (по умолчанию снята); оплата без галочки снимает
  прежнее согласие.
- Подписку продлевает только Result URL (подпись паролем №2); Success/Fail
  лишь возвращают владельца в личный кабинет.
- Возвраты — вручную в кабинете Робокассы.
- Оплаты в тестовом режиме (`ROBOKASSA_TEST=1` или `IsTest=1` в уведомлении)
  помечаются `test: true` и не идут в выручку и MRR панели платформы. Прошлые
  проверочные оплаты супер-админ отмечает тестовыми в «Аналитика → Последние
  оплаты» (`POST /saas/setBillingEventTest`).
- **Новая точка оплаченной сети** — только после оплаты
  (`/chainLocationQuote`, `/chainLocationCheckout`, назначение
  `chainLocation`): цена доп. точки за дни до конца оплаченного периода;
  точку создаёт подтверждённая оплата. В пробный период и для первой точки
  — бесплатно; `createTenant` с `chainId` в оплаченной сети отвечает 402.

### Оплата по счёту (ИП и организации)

Робокасса для самозанятых принимает только карты физических лиц и выдаёт
чек без ИНН покупателя, а при расчётах с ИП и организациями чек должен
содержать их ИНН (ст. 14 закона № 422-ФЗ, налог 6 %). Поэтому в личном
кабинете владелец выбирает «ИП или организация», вводит название и ИНН —
и получает счёт для оплаты переводом (реквизиты получателя — из «Панель
платформы → Безопасность → Платформа»).

- Реквизиты плательщика сначала пишутся в базу в РФ (pii-gateway, таблица
  `payer_requisites`), потом счёт — в Firestore (`bankInvoices`). pii-gateway
  ищется на `http://127.0.0.1:8080/`, затем `https://pii.zalpos.ru/`
  (или `PII_GATEWAY_URL`).
- Деньги пришли — «Панель платформы → Обзор → Счета ИП и организаций →
  Оплата получена»: подписка продлится.
- Затем в «Мой налог» — чек на ИП/организацию с ИНН из счёта, не позднее
  9-го числа следующего месяца; ссылку на чек вставить кнопкой «Чек выдан» —
  владелец увидит её в кабинете.

Как считается период: оплата раньше срока (или автопродление) добавляет
месяц/полгода/год к концу текущего оплаченного или пробного периода, а не
к сегодняшней дате. Оплата после просрочки снимает отсчёт до удаления
данных. Автопродление, льготный период и подсчёт usage — суточные задачи,
время их последнего прогона хранится в `platformStatus/cronJobs`, так что
перезапуск сервиса не сдвигает и не пропускает их.

## nginx — добавить маршрут `/saas/` к уже настроенному домену

Сервис использует тот же домен и сертификат, что и `pii-gateway`
(`pii.zalpos.ru`) — экономим ещё один цикл DNS+certbot. Добавьте в
`/etc/nginx/conf.d/pii-gateway.conf` внутри существующего блока `server {
listen 80/443 ...; server_name pii.zalpos.ru; ... }` ещё один `location`
ПЕРЕД блоком `location / { ... }` (порядок важен — nginx матчит более
специфичный префикс первым независимо от порядка в файле, но для
читаемости кладём его выше):

```nginx
location /saas/ {
    proxy_pass http://127.0.0.1:8081/;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
}
```

Обратите внимание на слэш в конце `proxy_pass http://127.0.0.1:8081/` — он
обрезает префикс `/saas/`, то есть запрос на `/saas/createTenant` уходит в
сервис как `/createTenant`. После правки: `nginx -t && systemctl reload
nginx`. Как только certbot выпустит сертификат для `pii.zalpos.ru`
(см. `pii-gateway/README.md`), он автоматически применится и к этому
`location` — отдельно ничего настраивать не нужно.

### Логотипы заведений — статика, отдельным `location`

Сама ЗАГРУЗКА логотипа (`POST /saas/uploadBrandingLogo`) идёт через
`location /saas/` выше как обычно — этот `location` нужен только для
ЧТЕНИЯ уже загруженных файлов, публично и без прокси до Node (та же идея,
что и у `/downloads/` для публичного APK, см. `saas/README.md`, раздел
8b). Добавьте в тот же `server { ... }` блок:

```nginx
location /branding/ {
    alias /opt/saas-gateway/branding-uploads/;
    add_header Cache-Control "no-cache";
}
```

`no-cache` — не «не кешировать вообще», а «перед показом закешированной
копии спросить сервер, не изменилась ли она» (обычный `ETag`/`If-None-Match`
у nginx работает из коробки) — логотип можно перезалить в любой момент, и
старая версия не должна залипать в браузере/CDN гостя. Файлы после
загрузки принадлежат пользователю `saas-gateway` (см. `setup.sh`) — чтобы
nginx (свой системный пользователь) мог до них дойти, родительские папки
должны быть проходимы, один раз:
```bash
chmod 755 /opt/saas-gateway /opt/saas-gateway/branding-uploads
```
(вторая папка появится сама при первой же загрузке логотипа — если ещё не
существует, `chmod` на неё можно пропустить до этого момента).
После правки конфига: `nginx -t && systemctl reload nginx`.

## ИИ-прокси и внутренняя сеть

`/aiProxy` ходит только по `https://` и только на внешние адреса: адрес
провайдера ИИ задаёт владелец заведения, и без этой проверки сервер по его
команде мог бы обращаться к `127.0.0.1`, соседним сервисам и метаданным
облака (SSRF). Переадресации провайдера не выполняются.

Переменная `AI_PROXY_ALLOW_PRIVATE=1` снимает это ограничение — **только для
локальных тестов** с мок-провайдером на `http://127.0.0.1`. На боевом сервере
её задавать нельзя.

## Консоль (`saas/console/console.js`)

Отредактируйте константу `SAAS_GATEWAY_URL` в начале файла на реальный
адрес (`https://pii.zalpos.ru/saas`) — до этого момента она пустая, и
кнопки «Создать заведение» / «Собрать APK» будут показывать понятную
ошибку вместо тихого падения.

## Проверка перед боевым использованием

- `npm test` (в папке `saas-gateway`) — smoke-тест валидации входа, не
  требует живой БД/Firebase.
- `systemctl status saas-gateway` и `journalctl -u saas-gateway -f` —
  статус и логи сервиса на сервере.
- Полный путь (создание заведения в консоли → присоединение устройства →
  касса работает) стоит проверить вручную хотя бы раз, тем же способом,
  каким это делали для pii-gateway.

## Резервные копии базы и проверка сертификатов

Сервис сам делает резервную копию всей базы Firestore раз в сутки (через
10 минут после старта, если последняя копия старше суток) в
`/opt/saas-gateway/backups/firestore-ГГГГ-ММ-ДДTЧЧ-ММ.json.gz` (права 600) и
хранит последние 14. Managed export Firestore недоступен без Blaze, поэтому
копия читает документы через Admin SDK — каждый документ это одно чтение
из бесплатной квоты (50 000 в сутки на Spark). Если в базе больше
`BACKUP_MAX_DOCS` документов, копия не делается, а раздел «Безопасность →
Платформа» объясняет почему. Там же — «Сделать копию сейчас» и скачивание
копии (только после ввода пароля, с записью в журнал безопасности).

Копии лежат на том же сервере — раз в неделю скачивайте свежую к себе.

Восстановление (перезаписывает документы тем, что было в копии; созданные
после копии документы не трогает):

```bash
cd /opt/saas-gateway
set -a; . /etc/saas-gateway.env; set +a
node restore-backup.js backups/firestore-...json.gz --dry-run          # сколько документов
node restore-backup.js backups/firestore-...json.gz --only=tenants/ID --yes   # одно заведение
node restore-backup.js backups/firestore-...json.gz --yes              # вся база
```

Бэкап одного заведения или сети скачивается кнопкой «Скачать бэкап» — владелец
в кабинете («Настройки»), супер-админ в карточке любого заведения или сети в
панели платформы (`POST /exportBackup` с `tenantId` или `chainId`). Файл —
обычный `.json` того же формата, восстанавливается тем же скриптом.
Из кабинета выгружается до `EXPORT_MAX_DOCS` документов (по умолчанию 15 000 —
чтобы не израсходовать дневную квоту чтений базы) и не чаще раза в 3 дня на
заведение или сеть (отметка — `backupExports/{tenant_|chain_}{id}`); в панели платформы
супер-админ выгружает без ограничения (`unlimited: true`, только после ввода
пароля):

```
node restore-backup.js zalpos-backup-...json --dry-run
node restore-backup.js zalpos-backup-...json --yes
```

Сертификаты HTTPS поддоменов заведений проверяются раз в сутки
подключением к локальному nginx (`127.0.0.1:443` с нужным SNI) —
предупреждение появляется за 14 дней до окончания или если сертификата
для поддомена нет.

Необязательные переменные окружения: `BACKUP_DIR`, `BACKUP_KEEP` (14),
`BACKUP_MAX_DOCS` (20000), `BACKUP_INTERVAL_HOURS` (24),
`GUEST_BASE_DOMAIN` (zalpos.ru), `GATEWAY_PUBLIC_HOST`
(pii.zalpos.ru), `CERT_CHECK_CONNECT_HOST` (127.0.0.1),
`CERT_CHECK_PORT` (443).

## Подозрительная активность

Каждое создание заведения, сети и демо, упор в лимит демо и отказ по
блокировке пишутся в `signupEvents` с IP (не в документ заведения — его
видят сотрудники). Раздел «Безопасность → Активность» группирует их по
IP за неделю. Блок-лист (`POST /blockEntry`, `/unblockEntry`) — IP-адреса
и домены почты, с которых нельзя создать заведение, сеть или демо
(массовые почтовики вроде gmail.com блокировать не даёт). Список кассовых
устройств (`POST /securityDevices`) берёт последнюю активность из Firebase
Auth (устройство обновляет токен примерно раз в час, пока касса работает);
`/disableDevice` отключает устройство целиком: членство, статус и сам
аккаунт с отзывом сеансов.

## Персональные данные (152-ФЗ)

Реестр запросов субъектов ПДн — `dataRequests`. Гость отправляет запрос
на удаление сам (кнопка «Удалить мои данные» в профиле веб-версии и
Android-приложения гостя → `POST /requestGuestDataDeletion`), остальные
запросы супер-админ заводит в «Безопасность → Данные»
(`/createDataRequest`, `/resolveDataRequest`); сроки по ст. 20 и 21 152-ФЗ: сведения и удаление — 10 рабочих дней, исправление — 7.
`POST /findGuest` ищет гостя по телефону во всех заведениях и сетях,
`POST /anonymizeGuest` (только после ввода пароля) обезличивает гостя:
в профиле остаются только обезличенные цифры, удаляются указатели
телефона и реферального кода, имя и телефон стираются из броней, листа
ожидания, заказов, вызовов и отзывов во всех точках, анонимный аккаунт
гостя удаляется. Сначала то же стирается в справочнике в РФ (pii-gateway,
`guest_forget`); `/findGuest` смотрит и туда (`guest_find_phone`).

### Хранение только в РФ (режим rf)

Заведение в режиме `meta/venueProfile.piiMode = 'rf'` не держит в Firestore
имён, телефонов и адресов — только id; сами значения лежат в справочнике
pii-gateway в РФ. За границу ничего не передаётся, и заведению из-за ZalPOS
не нужно подавать в Роскомнадзор ни уведомление, ни сведения о
трансграничной передаче.

- Новые заведения создаются сразу в режиме rf, когда справочник подключён
  (`PII_INTERNAL_TOKEN` задан). Запасной выход при сбое справочника —
  `NEW_TENANTS_PII_MODE=mirror` в `/etc/saas-gateway.env`.
- Действующие заведения переводит супер-админ: «Заведения» → карточка →
  «Персональные данные: где хранятся» (`POST /piiMigration`, pii-migrate.js):
  1) «Перенести в РФ» — копия из Firestore в справочник, только дописывает
  пустое; 2) «Переключить» — когда все кассы на новой сборке (касса сама
  отмечает `devices/{uid}.piiReady`); 3) через сутки «Пробная очистка» и
  «Очистить Firestore» — убирается только то, что сверено со справочником.
  Ход и итог — в `tenants/{id}/meta/piiMigration`. «Вернуть обычный режим» —
  откат на случай проблем.

## Реквизиты платформы (оферта, политика ПДн, подвал сайта)

Панель платформы → «Безопасность» → «Платформа» → «Реквизиты»: ФИО ИП
(или название организации), ОГРНИП/ОГРН, ИНН, адрес, банк, e-mail,
номер в реестре операторов ПДн. Сохранение — `POST /savePlatformLegal`
(повторный ввод пароля, запись в журнал безопасности), хранятся в
`platformConfig/legal` (читают все, пишет только сервер). Они
подставляются в оферту и политику вместо «[указать]» и выводятся в
подвале сайта — без них нельзя принимать оплату (54-ФЗ, модерация
Робокассы). Пока не заполнены, чек-лист раздела показывает красный пункт.

## ИИ: ключи провайдеров и гостевой прокси

Настройки ИИ заведения разделены на два документа:
`tenants/{id}/meta/aiSettings` — включено ли, провайдер (Tooken Club,
DarkAPI, Google Gemini или свой шлюз), резервный провайдер, модели,
агенты; его читают и гости. Ключи и адреса — в `meta/aiSecrets`, его
читает только персонал (касса вызывает ИИ напрямую). Правила базы не
дают снова положить ключ в `aiSettings`.

Гостевое приложение ключей не видит и спрашивает ИИ через
`POST /aiProxy`: сервер проверяет, что это гость или сотрудник этого
заведения, подставляет адрес и ключ провайдера, ставит модель только из
настроек заведения, режет лимит ответа до «Лимит ответа × 2» и держит
лимит 30 вопросов за 10 минут на гостя. При отказе основного провайдера
приложение повторяет вопрос через резервный.

Через 2 минуты после запуска сервер один раз переносит ключи, сохранённые
старыми версиями кассы прямо в `aiSettings`, в `aiSecrets`. Кассы и
гостевые APK, собранные до этого обновления, читали ключ из `aiSettings`
и после переноса останутся без ИИ — их нужно пересобрать («Собрать APK»
в консоли) и обновить на устройствах.

У сети заведений ключи и настройки ИИ общие на все точки
(`chains/{chainId}/meta/aiSettings` и `aiSecrets`): владелец вводит ключ
один раз в кабинете → «ИИ» (или в кассе → Админ → Настройки ИИ), и он
работает во всех точках; прежние настройки точки переносятся в сеть при
первом сохранении. У одиночного заведения — свои ключи.

Gemini из России не отвечает (ограничение Google по региону): укажите
прокси в «Адрес API» или назначьте резервным провайдером DarkAPI/Tooken
Club.

## ИИ-бот поддержки в Telegram (`support-bot.js`)

Один бот на всю платформу. Настраивается в панели супер-админа →
«Поддержка» → «ИИ-бот поддержки в Telegram»: токен из @BotFather (отдельный
бот, не бот заведения), ID рабочей группы с «Темами» (или код `/link …` в
группу), Telegram ID сотрудников, провайдер и ключ ИИ. Токен и ключ хранятся
в `supportBot/config` зашифрованными тем же ключом, что и токены ботов
заведений (`TELEGRAM_SECRET_KEY` / `TELEGRAM_KEY_FILE`); в панель не
возвращаются.

- Обновления приходят на `/tgHook/_support` (через `TELEGRAM_HOOK_BASE`, если
  задан ретранслятор). Бот в группе — администратор с «Управлением темами».
- Каждое обращение (из Telegram или из «Поддержки» кабинета) — тема в группе.
  ИИ отвечает первым; слова «оператор», «верните деньги», жалоба, суд и т. п.,
  кнопка «👤 Позвать человека» или маркер `[[ОПЕРАТОР]]` в ответе ИИ — тема 🔴,
  сигнал сотрудникам в личку, ИИ молчит. Ответ сотрудника в теме уходит
  клиенту и ставит ИИ на паузу (по умолчанию 12 ч, /ai — вернуть).
- Контекст ИИ: 3 статьи инструкции (`kb/guide.mjs` — копия
  `saas/console/guide.js`, кладёт `update-server.sh`) и база поддержки — до 4 статей, до 3 записей базы знаний
  `supportKnowledge`, состояние заведения, ошибки журнала по нему за сутки,
  краткая память прошлых обращений. Телефоны, почты, ИНН, ники и секреты
  маскируются до отправки провайдеру. Суточный лимит ответов — в панели.
- Знания: инструкция кабинета, статьи поддержки `support-kb.js` (устройства,
  установка, оплаты, неполадки, законы для общепита), частые вопросы кабинета
  (`FAQ_ITEMS`, копия `kb/console.js`) и живые тарифы из `plans`. В «Состоянии»
  — что настроено в кассе (онлайн-касса, терминал, онлайн-оплата, реквизиты,
  принтер, ЕГАИС, меню, столы) — только признаки, без логинов и ключей.
- Документы: `support-docs.js` собирает .docx (приказ об ответственном за ПДн,
  политика, согласие и обязательство работника, лист ознакомления, памятка РКН,
  уголок потребителя) с реквизитами из `meta/venueProfile` и `platformConfig/legal`;
  кнопка «📄 Документы», ИИ предлагает документ маркером `[[ДОКУМЕНТ: id]]`.
- ИИ (`support-ai.js`): несколько провайдеров и ключей по порядку (Tooken,
  DarkAPI, OpenRouter, DeepSeek, OpenAI, Anthropic, Gemini, свой шлюз); у
  каждого лёгкая и сильная модель — не указаны, бот берёт проверенные или
  выбирает по списку `/models`. Режим «авто»: юридические, расчёты, длинные
  вопросы и долгие диалоги — сильной моделью, остальное — лёгкой. Кончился
  баланс — ключ отдыхает 6 ч, не принят — час, 429 — минуту; бот переходит к
  следующему и пишет админам. Состояние ключей — `supportBot/aiStatus`.
- Админка в Telegram: ID из поля «Администраторы бота» видят кнопку
  «⚙️ Админка» — ИИ вкл/выкл, режим, ключи (вкл/выкл, порядок, проверка,
  подбор моделей), лимит, пауза, часы работы, сотрудники, приветствие, база
  решений, ждущие обращения, статистика, проверка ИИ. Сами ключи меняются
  только в панели — в переписку Telegram они не попадают.
- Карта кода (`build-code-map.js`, при обновлении сервера → `kb/code-map.json`):
  по каждому файлу касс, сервера, кабинета и веба гостя — описание из
  комментариев, классы и надписи на экранах. Самого кода, ключей, адресов,
  почт и телефонов в карте нет; файлы настроек и ключей не читаются. ИИ
  берёт до 2 файлов под вопрос, клиенту отвечает через экраны и кнопки;
  `guardReply` вычищает из ответа имена файлов, пути в базе, IP и служебные
  адреса. Сотрудникам в теме — «🧩 код: …».
- Клиент зовёт бота («бот, помоги», «ИИ ответь», «пусть ответит бот», «нет, бот») —
  пауза после человека снимается и ИИ отвечает на нерешённый вопрос; ИИ выключен
  в теме вручную (/mute) — клиенту «занимается специалист», в теме подсказка.
- Поиск в интернете (support-web.js): по внешним вопросам (законы, банки, ОФД,
  оборудование, «где купить») ИИ-планировщик решает, искать ли, бот ищет
  (без ключа — DuckDuckGo; с ключом — Brave, Tavily, Serper), читает 2 страницы
  (только внешние https, проверка адреса как у ИИ) и отвечает со ссылкой на
  источник; о функциях ZalPOS интернету не верит. До 8 поисков на обращение,
  300 в сутки. Настройка — панель «Бот поддержки» и «🌐 Интернет» в админке бота.
- Модель под задачу: сильная — законы, расчёты, скриншоты, ответ по найденному в
  интернете, недовольство («не то», «не работает»), долгий диалог; иначе лёгкая.
- Защита от обмана: `deceitSignals` распознаёт смену роли («забудь инструкции»,
  «режим разработчика»), выведывание промпта и ключей, «я разработчик ZalPOS»,
  подделку «[Специалист поддержки]» и маркеров `[[…]]`, просьбы о чужих данных,
  ссылки на несуществующие обещания и «запросы от органов» — в тексте и на
  скриншотах. ИИ получает предупреждение и отвечает сильной моделью, в теме —
  «🛡»; после 3 попыток в обращении — человек. Реплики клиента для ИИ
  обезврежены (`neutralize`). Ссылки «под ZalPOS» на чужих доменах
  (`suspiciousLinks`) — ИИ предупреждает о фишинге. Ответ ИИ с обещанием денег,
  скидки, бесплатного периода или сроков (`promisesSomething`) клиенту не
  уходит — зовём специалиста.
- Живой разговор: «да»/«ок»/«вы тут?» после вопроса бота — это ответ, бот
  выбирает вероятный вариант и не переспрашивает; клиент дописал, пока ИИ думал, —
  устаревший ответ не отправляется; в кабинете «Ассистент печатает…» (aiTypingAt).
- Сотрудники: обращение ведёт один (assigneeId) — при «нужен человек» бот
  назначает по очереди, в личку всем: «Назначено вам» / «на подхвате»; первый
  ответивший становится исполнителем. Ответ другого сотрудника клиенту не уходит
  — в теме «✋ … ведёт @…» и «🙋 Перехватить». Клиент ждёт ответа человека 15 мин
  (clientAt) — sweepSla раз в минуту передаёт следующему и напоминает всем.
  Юзернеймы — supportBot/staffDir (запоминаются, когда сотрудник пишет).
- Темы: одна на клиента (`supportTopics/{t_заведение|u_tgId|o_uid}` → topicId).
  Новое обращение того же клиента — в его тему (тема переоткрывается, сверху
  «🆕 Новое обращение #N»); ответ из темы — в текущее обращение (открытое, иначе
  последнее); тема закрывается, когда закрыты все обращения в ней.
- Автообучение (`autoLearn`, по умолчанию включено): после ответа человека и
  «спасибо», 👍, оценки 4–5, закрытия или 15 минут тишины ИИ сам решает, есть
  ли решение для других клиентов (ответы специалиста — главный источник),
  обобщает без персональных данных и сохраняет или дополняет похожую запись.
  Раз на обращение, пока не появятся новые ответы людей. Отвечал специалист,
  а бот решил не запоминать — пишет в теме почему, с кнопкой «Всё равно запомнить».
- Обучение вручную: «📚 Запомнить» / `/learn` в теме — ИИ обобщает решение в запись
  базы знаний без персональных данных; `запомни: текст`, `/learn текст` или
  reply на своё сообщение словом «запомни» — сохраняет текст специалиста как
  есть (клиенту не уходит); в админке бота — «➕ Добавить вручную». После
  закрытия — кнопки «📚 Запомнить» и «↩️ Открыть снова»; меню «/» в группе
  со всеми командами. 👍 клиента поднимает запись выше.
  Неудачные записи удаляются в панели («Чему научился бот») или кнопкой.
- Тесты: `node test.support.js`.

## Демо-режим

Кнопка «Демо» в приложении (см. `SaasDevicePairingScreen`) вызывает
`POST /saas/createDemoTenant` — сервис сам создаёт одноразовую демо-сеть из
двух точек («Центр»: 1111/2222/3333/111111, «Набережная»: 4444/5555/6666/222222)
с заготовленными столами/меню, общими гостями и бонусами и возвращает код
приглашения первой точки и код демо-сети (`chainSlug`) для демо приложения
гостя; касса присоединяется тем же путём, что и обычное устройство, и при
входе спрашивает, в какую точку войти.
Демо-заведения живут 3 дня (`DEMO_TTL_MS`, у заведения — `demoExpiresAt`) и
стираются сами (см. `scheduleDemoCleanup` в `server.js`): раз в 30 минут
сервис ищет заведения с `demo: true` старше этого возраста и полностью их
удаляет. Касса к этому моменту сама открывает новое демо в исходном виде
(`DemoGate` в приложении) — так демо нельзя использовать как рабочую кассу.
Ограничение — не больше 5 демо-заведений в час с одного IP (защита от
накрутки).

## Письма входа в оформлении ZalPOS

Письма со ссылкой для входа, сменой пароля и подтверждением почты сервис
отправляет сам (`POST /sendAuthEmail`, шаблон — `auth-email.js`), потому что
текст писем Firebase в его консоли не редактируется. Нужен SMTP-ящик на
домене платформы — добавьте в `/etc/saas-gateway.env` и перезапустите сервис:

```
SMTP_HOST=smtp.yandex.ru
SMTP_PORT=465
SMTP_USER=noreply@zalpos.ru
SMTP_PASS=<пароль приложения для этого ящика>
MAIL_FROM=ZalPOS <noreply@zalpos.ru>
```

Пока эти переменные не заданы (или SMTP не отвечает), консоль отправляет
письма через Firebase, как раньше. Лимиты: 10 писем в час с одного IP и 5 в
час на один адрес.
