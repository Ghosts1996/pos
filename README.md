# Colibri — система для кальянной

Три приложения на одной базе Firebase:

- **Hookah POS** (`lib/main.dart`, пакет `com.hookahpos`) — планшет за стойкой:
  карта зала, чек, склад, отчёты, интеграции, ИИ-помощники для персонала.
- **Colibri Lounge** (`lib/client/kolibri_main.dart`, пакет `com.kolibrilounge`) —
  Android-приложение гостя: бронь, меню, свой счёт за столом, бонусы, ИИ-консьерж.
- **Веб-версия гостя** (`public/app/`, `colibri-lounge.web.app/app/`) — та же
  логика, что в Android-приложении, но в браузере — специально для iPhone,
  куда нативное приложение не поставить без Apple Developer аккаунта.

Все три части читают и пишут в один и тот же проект Firebase (Firestore +
Hosting), работают на бесплатном тарифе **Spark** — без кредитной карты,
без Cloud Functions (см. раздел ниже, чем они заменены).

Кассового аппарата с фискализацией по умолчанию нет — это открыто написано
в самом приложении (экран Настройки → Интеграции) и подробно объяснено в
разделе «Фискализация и оборудование» ниже: приложение считает суммы и ведёт
чек, но настоящую фискализацию, ЕГАИС и эквайринг нужно либо настроить
самому (для части — есть готовый рабочий клиент), либо принять, что это
имитация.

## Состав проекта

```
lib/
  main.dart                 — точка входа POS
  client/kolibri_main.dart  — точка входа Android-приложения гостя
  models/                   — модели данных (общие для POS и гостя)
  services/                 — вся бизнес-логика и интеграции
  services/ai/              — ИИ-агенты, инструменты, клиент LLM-шлюза
  screens/employee/*        — экраны сотрудника
  screens/admin/*           — экраны администратора
  client/screens/*          — экраны Android-приложения гостя
  client/services/*         — сервисы гостевого приложения (уведомления, deep links)
  widgets/                  — переиспользуемые виджеты (таймер, ИИ-чат и т.п.)
public/
  index.html                — страница «установить приложение» без привязки к столу
  table.html                — страница QR-кода конкретного стола (редирект в приложение)
  app/                       — веб-версия гостя (app.js, app.css, index.html, manifest)
firestore.rules              — правила безопасности (реальная защита данных —
                                проверки в самом приложении лишь для UX)
.github/workflows/build-apk.yml — сборка APK в GitHub Actions
deploy.sh                    — одна команда, которая выкатывает правила,
                                индексы и веб-хостинг в Firebase
```

Папок `android/`, `ios/` в репозитории нет — CI сам генерирует их при каждой
сборке той версией Flutter, что установлена на раннере, это исключает
рассинхрон версий Gradle/AGP.

## Hookah POS — возможности сотрудника

- **Карта зала** (`floor_plan_screen.dart`) — живая схема столов, у каждого
  стола таймер сеанса, метка с именем гостя, счётчик открытых чеков. Баннер
  сверху показывает вызовы и заказы из гостевого приложения в реальном
  времени — тап сразу открывает нужный стол. Кнопка ИИ-помощника зала
  (видит зал, брони, склад).
- **Экран стола/чека** (`table_detail_screen.dart`) — начать сеанс (90 минут
  по умолчанию, можно сразу указать имя гостя), несколько одновременных
  чеков на одном столе (сплит-биллинг, с переключателем между ними),
  перезабивка (полный сброс таймера) и точечное «обновить таймер»
  (+15/+30/+60 или −15 минут), применение скидочной карты по номеру,
  перенос сеанса на другой стол с сохранением заказа, таймера и истории,
  список позиций заказа со степперами количества и итогом с учётом скидки.
- **Оплата и закрытие чека** (`payment_screen.dart`) — сплит-оплата
  наличные / карта / «терминал» / «за счёт заведения», быстрые суммы,
  автоподстановка сдачи, списание бонусов и активация сертификата гостя,
  оплата через подключённый платёжный терминал, печать нефискального чека
  на принтере и (если настроена онлайн-касса) отправка фискального чека с
  кодами маркировки «Честного знака» и, при наличии алкоголя, документа в
  ЕГАИС. При успешной оплате гостю начисляется кешбэк и, если это его
  первый визит по реферальному коду, — бонус за приглашение.
- **Добавление позиций в чек** (`menu_selection_screen.dart`) — категории и
  сетка позиций, поиск по всему меню, сканирование штрихкода/кода маркировки
  сканером-«пистолетом» (HID) в фоне или камерой планшета: код сначала
  пробуют разобрать как DataMatrix «Честного знака» (с защитой от повторной
  продажи и опциональной онлайн-проверкой), если не вышло — как обычный
  штрихкод склада.
- **Кухня/бар** (`kds_screen.dart`) — очередь вызовов гостей и заказов из
  приложения, карточки краснеют по истечении 5 минут; можно отметить вызов
  выполненным, принять заказ в чек или отклонить с причиной, отметить заказ
  готовым (гость получает уведомление).
- **История чеков** (`receipts_history_screen.dart`) — закрытые чеки за
  период с составом и способом оплаты, оформление возврата (бухгалтерская
  отметка, не возврат по карте).
- **Брони** (`reservations_screen.dart`) — брони на выбранный день из
  гостевого приложения и добавленные вручную («бронь по телефону»),
  автоподбор или ручной выбор стола с учётом занятости, подтверждение,
  посадка (открывает чек и переносит предзаказ), отметка неявки, отмена.
  Кнопка ИИ-разбора броней на смену.
- **Лист ожидания** (`waitlist_screen.dart`) — очередь живых гостей без
  брони, сортировка по времени ожидания, оценка ожидания по реальным
  таймерам столов (не «на глаз»), приглашение («стол готов» — с
  уведомлением гостю), посадка, перевод в бронь, отметка «ушёл».
- **Склад — только просмотр** (`stock_view_screen.dart`) — остатки по
  категориям, отметка позиций на исходе.
- **Инвентаризация** (`inventory_count_entry_screen.dart` +
  `inventory_count_screen.dart`) — снятие остатков: снапшот системных
  количеств, ввод фактических (автосохранение), расхождения показываются
  сразу, история прошлых пересчётов.
- **Х-отчёт по смене** (`x_report_screen.dart`) — продажи за текущую/прошлую
  смену или произвольный период, с фильтром по сотруднику, разбивкой по
  позициям и способам оплаты, отметками неоплаченных закрытий и возвратов;
  открытие/закрытие смены как отдельная сущность (не привязана к календарным
  суткам). «Распечатать отчёт» копирует текст в буфер обмена.

## Hookah POS — возможности администратора

- **Отчёты** (`reports_screen.dart`) — выручка, число визитов, средний чек,
  количество перезабивок, разбивка по сотрудникам, топ-15 позиций меню,
  сумма скидок по картам, отметки неоплаченных закрытий и возвратов —
  единственный источник финансовых цифр вместо Z-отчёта. Копирование в
  буфер текстом.
- **Редактор карты зала** (`floor_plan_editor_screen.dart`) — добавление,
  перетаскивание, изменение формы (прямоугольник/круг) и вместимости
  (сколько чеков разрешено одновременно) столов; удалить занятый стол нельзя.
- **Меню** (`menu_editor_screen.dart`) — категории и позиции, фото (галерея
  или камера), вес/единица, доступность, привязка к позиции склада для
  автосписания (в том числе «составные» позиции из нескольких ингредиентов).
- **Скидочные карты** (`discount_cards_screen.dart`) — CRUD по номеру, имени
  гостя, проценту скидки.
- **Подарочные сертификаты** (`gift_cards_screen.dart`) — выпуск кода
  (например, для публикации в Telegram-канале): фиксированная сумма
  бонусов КАЖДОМУ активировавшему, лимит активаций (или без лимита), срок
  действия, комментарий. Это код на массовую раздачу бонусов, а не
  именной сертификат с балансом.
- **Сотрудники** (`employees_screen.dart`) — имя, 4-значный PIN, роль
  (сотрудник/администратор). Вход в приложение целиком держится на PIN —
  отдельных логинов/паролей нет.
- **Гости** (`guests_screen.dart`) — карточки профилей из гостевого
  приложения: уровень, кешбэк, визиты, потрачено, баланс бонусов, поиск по
  имени/телефону; смена номера телефона, удаление гостя, объединение двух
  профилей при смене телефона гостем (по номеру + короткому коду
  устройства, который гость называет с экрана «Профиль»).
- **Интеграции** (`integrations_settings_screen.dart`) — центральный экран
  для всего оборудования и фискальных сервисов, подробности — в разделе
  «Фискализация и оборудование» ниже. Каждый блок с собственной кнопкой
  проверки связи.
- **Склад** (`inventory_screen.dart`) — CRUD позиций любой единицы измерения
  (г/кг/мл/л/шт), порог «на исходе», приход/списание/ручная корректировка с
  причиной и полной историей движений (`inventory_item_detail_screen.dart`),
  тот же экран инвентаризации, что у сотрудника.
- **ИИ-аналитика** (`ai_insights_screen.dart`) — готовые разборы одной
  кнопкой (продажи, заявка на закупку, отзывы гостей, идеи акций, брони на
  смену) и свободный диалог с аналитиком.
- **Настройки ИИ** (`ai_settings_screen.dart`) — шлюз LLM, ключ, модели,
  температура/лимит токенов, включение агентов по отдельности, расход
  токенов по агентам за 30 дней.
- **Журнал** (`activity_log_screen.dart`) — сводки ИИ (дни рождения,
  неявки, риски по складу), журнал действий ИИ (что именно поменял
  ассистент и когда), журнал кассы (удаления позиций, закрытия без оплаты,
  скидки, возвраты, изменения таймера, корректировки склада) с кнопкой
  «Проверить» — ИИ-аудитор ищет аномалии за неделю.
- **Отзывы** (`reviews_screen.dart`) — входящие оценки гостей, фильтр по
  рейтингу, средняя оценка, звонок гостю в один тап, ИИ-резюме отзыва.
- **Афиша / контент-лента** (`stories_editor_screen.dart`) — карточки для
  гостевых приложений (заголовок, текст, картинка, кнопка на меню/бронь,
  порядок, публикация); можно попросить ИИ сгенерировать черновики —
  публикуются только вручную.
- **Профиль заведения** (`venue_profile_screen.dart`) — адрес, телефон,
  описание, правила, координаты (для погоды в ИИ), часы работы по дням
  недели (в том числе «за полночь»), FAQ, счастливые часы (автоскидка по
  дню/времени), тумблер «Cloud Functions подключены».
- **QR-коды столов** (`table_qr_screen.dart`) — генерация и печать QR на
  страницу `/table/{id}`, которая сама разбирается, открыть ли приложение
  или показать установку.

## Фискализация и оборудование: что реально работает, а что — заготовка

Экран Настройки → Интеграции прямо на месте объясняет статус каждого пункта.
Здесь — то же самое сводкой:

| Интеграция | Статус |
|---|---|
| **Онлайн-касса (54-ФЗ)** | По умолчанию — имитация (`MockKassaService`): ничего не уходит в ФНС. Есть два реально работающих облачных провайдера, оба с опросом статуса до получения настоящего номера ФД/ФПД: **АТОЛ Онлайн** (`AtolCloudKassaService`, протокол v4 — им же говорят некоторые реселлеры вроде Ferma/OFD.ru, нужно только сменить адрес API) и **OrangeData** (`OrangeDataKassaService`, отдельный протокол на mTLS + RSA-подписи запроса; маркированные товары пока не поддержаны — для них используйте АТОЛ). Плюс честная заготовка **CloudKassir** — поля сохраняются, но протокол фискализации не реализован, пока не появится открытая документация. Любой из реальных вариантов включается в Настройки → Интеграции сразу после того, как заключён договор с провайдером и с ОФД и получены реквизиты — дописывать код не нужно. |
| **Честный ЗНАК (маркировка)** | Разбор кодов DataMatrix — настоящий. Локальная защита от повторной продажи одного и того же экземпляра — настоящая. Онлайн-проверка кода через реальный API «Честного знака» — настоящая (нужен токен). Юридическое «списание» кода при продаже (тег 1162) возможно только через реальную фискальную кассу — раз касса имитируется по умолчанию, вывод из оборота фактически не происходит. |
| **ЕГАИС** | Настоящий HTTP/XML-клиент к УТМ (Универсальному Транспортному Модулю). Работает, только если в заведении физически установлен и настроен УТМ с крипто-ключом (JaCarta/Rutoken) — само приложение УТМ не заменяет и не эмулирует. |
| **Принтер чеков** | Настоящая печать по Bluetooth или Wi-Fi/LAN (ESC/POS) — но чек нефискальный, информационный. |
| **Терминал оплаты — Ручной** | Всегда доступен, работает с любым физическим терминалом любого банка: кассир сам подтверждает в приложении, что оплата на терминале прошла. |
| **Терминал оплаты — Т-Банк QR СБП** | Настоящая рабочая интеграция (Init → GetQr → GetState с публичным API интернет-эквайринга): отдельный терминал не нужен, гость платит по QR из своего банковского приложения. |
| **Терминал оплаты — Сбер / ВТБ / Альфа-Банк / Точка / mPOS / Ingenico / Verifone** | Честные заготовки: поля для реквизитов в настройках уже есть и сохраняются, но HTTP/SDK-вызовов ещё нет — ждут технической документации по договору эквайринга с конкретным банком. |

Причина, по которой это не «дописано»: настоящая интеграция с каждым банком
или ФНС требует подписанного договора и закрытой документации/SDK конкретного
провайдера — это нельзя реализовать вслепую без риска выдать несуществующую
интеграцию за рабочую.

## Программа лояльности, бонусы и гостевые механики

**Уровни и кешбэк** (`ClientProfile.tiers`, посчитаны от суммы всех оплаченных
визитов, без срока действия бонусов):

| Уровень | Порог (потрачено) | Кешбэк |
|---|---|---|
| Бронза | 0 ₽ | 3% |
| Серебро | 10 000 ₽ | 5% |
| Золото | 25 000 ₽ | 7% |
| Платина | 50 000 ₽ | 10% |
| Алмаз | 100 000 ₽ | 15% |

- Бонусами можно оплатить **до 50% чека**, списывает кассир на кассе
  (`BonusRedeemPanel`) — сам гость списать бонусы не может.
- **Реферальная программа** — у каждого гостя свой код `KLB-XXXX`; новый
  гость может ввести чужой код до своего первого визита. После первого
  **оплаченного** визита приглашённый получает 200 бонусов, пригласивший —
  300 (защита от накрутки: только один раз, только по факту оплаты).
- **Подарочные сертификаты** — не именной баланс, а код на массовую раздачу:
  фиксированная сумма бонусов каждому из первых N активировавших. Гость
  вводит код, заявка уходит на кассу и обрабатывается в порядке поступления
  (гость не может начислить бонусы себе сам — это заблокировано правилами
  базы).
- **Лист ожидания** — гость может встать в очередь прямо из приложения,
  видит оценку ожидания, посчитанную по реальным таймерам столов, и статус
  «стол готов».
- **Отзывы** — после визита гостю показывается форма оценки (звёзды + текст),
  отзывы видны администратору с ИИ-резюме.
- **Чаевые** — гость выбирает сумму (200/500/1000 ₽) кальянщику; это запись
  намерения и уведомление персоналу, реального списания денег с карты гостя
  в этой части кода нет — приём оплаты чаевых предстоит подключить отдельно.

## Искусственный интеллект

ИИ подключается не напрямую к Anthropic/OpenAI, а через настраиваемый
шлюз (`tooken_client.dart`) — HTTP-клиент, совместимый и с OpenAI-, и с
Anthropic-форматом API (формат определяется автоматически), с retry,
кэшем ответов, поддержкой tool-calling и логированием расхода токенов по
агентам. Экран Настройки → ИИ подсказывает конкретные готовые шлюзы, но
подойдёт любой совместимый.

16 агентов (`ai_agents.dart`), каждый со своим системным промптом и списком
разрешённых инструментов:

- **Зал и гости**: `hall` (ассистент зала — видит зал/брони/склад),
  `hookah_sommelier` (подбор микса по вкусу/погоде/времени суток),
  `upsell` (допродажи по текущему чеку), `hostess` (конфликты броней, риск
  неявки), `concierge` (ИИ-консьерж в приложении гостя — меню, бронь, свой
  счёт, бонусы, вызов персонала).
- **Деньги и склад**: `analyst` (разбор продаж), `inventory` (заявка на
  закупку, риски стоп-листа), `pricing` (меню-инжиниринг), `forecaster`
  (прогноз загрузки), `auditor` (поиск аномалий — закрытия без оплаты,
  подозрительные скидки/возвраты).
- **Маркетинг и контент**: `marketing` (идеи акций), `loyalty`
  (персональные сообщения для возврата гостей), `storyteller` (черновики
  карточек афиши), `menuWriter` (описания позиций меню).
- **Качество и команда**: `quality` (кластеризация тем отзывов, черновики
  ответов), `shiftCoach` (разбор смены).

Инструменты, которые ИИ реально может вызывать (`ai_tools.dart`), с
разграничением по области (сотрудник/гость) и логированием каждого
изменения в журнал действий: чтение меню/зала/склада/броней/продаж/отзывов/
профиля гостя/погоды (реальный запрос к Open-Meteo по координатам заведения)
— и запись: создать бронь, включить/выключить позицию меню, добавить
заметку к брони, вызвать персонал (только для гостя), сохранить вкусовые
предпочтения гостя, оставить заметку персоналу.

Фоновые ИИ-задачи (`ai_scheduler.dart`) на «дежурном» планшете: утренний
бриф хостес, наблюдение за складом каждые 3 часа, дайджест отзывов раз в
сутки, разбор смены по ночам.

## Android-приложение гостя «Colibri Lounge»

- **Вход** — анонимно и без пароля; «своим» гостя делает введённый один раз
  номер телефона (без SMS-подтверждения; после сохранения номер меняет
  только персонал). Короткий код устройства (6 символов) на экране профиля
  нужен, если гость сменит телефон — персонал объединит историю по номеру
  + коду.
- **Главная** — баланс бонусов, уровень и прогресс до следующего, «Афиша»
  (карточки с новостями/акциями — ссылки в тексте кликабельны), карточка
  ближайшей брони, баннер активного визита, быстрые действия («Забронировать»,
  «Меню», «Подбор кальяна» — открывает ИИ в режиме сомелье, «Я за столом» —
  сканер QR).
- **Бронирование** — выбор даты (14 дней вперёд), числа гостей, длительности
  (1/1.5/3/4.5 часа), реальных свободных слотов (учитывает и брони, и уже
  открытые сеансы), сводка по слоту (сколько столов свободно/забронировано/
  занято/«впритык»), ручной выбор стола на карте зала или автоподбор,
  комментарий-пожелание, необязательный предзаказ из меню, список своих
  броней с отменой.
- **Карта зала** — только просмотр: открыть чужой/свободный стол из
  приложения нельзя, сесть можно только физическим сканированием QR на
  столе (защита от удалённого «захвата» чужого стола).
- **Меню** — категории, поиск, фото; заказ прямо из приложения возможен
  только когда гость уже сидит за столом — заказ уходит персоналу на
  подтверждение, а не сразу в чек.
- **Мой стол** (пока сидит за столом) — таймер сеанса, кнопки вызова
  персонала (угли, перезабивка, позвать кальянщика, счёт), живой чек с
  позициями и итогом, статус заказов из приложения, доступный баланс
  бонусов (списывает кассир), кнопка «это не мой стол». После закрытия
  чека — экран благодарности с формой оценки.
- **Профиль** — имя, телефон (разово), карточка уровня и прогресса, код
  устройства для объединения истории, история визитов и история операций
  с бонусами, диагностика уведомлений.
- **Ещё** — чаевые кальянщику, активация подарочного сертификата (с живым
  статусом заявки), лист ожидания (встать/выйти из очереди), свой
  реферальный код и поле для ввода чужого.
- **ИИ-консьерж/сомелье** — плавающая кнопка на любой вкладке; доступен,
  только если у гостя указан телефон, он сидит за столом (`activeSession`)
  и не исчерпал дневной лимит вопросов (10 в день). Знает реальные меню,
  свободные слоты, баланс и уровень гостя, умеет создавать бронь (всегда
  переспрашивает детали), вызывать персонала, запоминать вкусовые заметки,
  честно объясняет бонусную программу по реальным цифрам, а не выдумывает.
- **Уведомления** — полностью локальные (без сервера): реактивные, пока
  приложение открыто/в фоне (статус брони, статус заказа, начисление
  бонусов), и отложенные системные — за час и за 20 минут до брони (с
  кнопками «Приду»/«Не приду» прямо в уведомлении) — эти срабатывают даже
  при закрытом приложении и без сети.

## Веб-версия для гостей (iPhone)

Рукописное SPA на чистом JS (`public/app/app.js`, без сборщика, Firebase
подключается прямо из браузера), потому что нативное Android-приложение на
iPhone не поставить без Apple Developer аккаунта. Логика продублирована
«1 в 1» с Android-приложением гостя, кроме двух осознанных исключений:

- **Нет ИИ-чата** — ключ LLM-шлюза нельзя безопасно передать в браузер.
- **Нет настоящих push-уведомлений** — у браузера нет фонового push той же
  надёжности, что у нативного приложения; вместо этого на Главной и на
  экране брони есть карточка-напоминание, которая обновляется каждые 30
  секунд, пока вкладка открыта.

Всё остальное реализовано так же, как в Android-приложении: главная с
балансом и афишей (ссылки в тексте кликабельны), меню с заказом при
активном сеансе, бронирование с реальным подбором слотов и стола, карта
зала только на просмотр, сканер QR прямо в браузере (нативный
`BarcodeDetector` в Chrome/Android, откуда его нет — библиотека `jsQR` для
Safari/iPhone), привязка к столу с тем же требованием указанного телефона
и тем же выбором чека при сплит-биллинге, живой чек и вызов персонала,
профиль с историей визитов и бонусов, раздел «Ещё» — чаевые, сертификат,
лист ожидания, реферальный код.

Установка на iPhone — через Safari «На экран Домой» (manifest.webmanifest
+ мета-теги `apple-mobile-web-app-*`), с учётом безопасной зоны под чёлкой/
статус-баром (`env(safe-area-inset-*)`), чтобы верхние кнопки не уезжали
под системную шторку.

Страница `colibri-lounge.web.app/table/{id}` (QR на столе) сама решает,
что показать: на iPhone сразу открывает веб-версию на этом столе, на
Android пробует открыть нативное приложение по `intent://`, а если оно не
установлено — через 2.5 секунды показывает ссылки на скачивание (Яндекс
Диск, Google Диск) и ссылку на веб-версию. Старые наклейки со схемой
`kolibri://table/{id}` по-прежнему открывают приложение, если оно уже
стоит — просто не показывают подсказку об установке, если его нет.

## Как запустить проект с нуля

### 1. Подключить Firebase

```bash
dart pub global activate flutterfire_cli
flutterfire configure
```

Команда попросит выбрать/создать проект и сама перезапишет
`lib/firebase_options.dart`. Если запустить приложение до этого шага — оно
не упадёт, а покажет экран-инструкцию на русском (`SetupRequiredScreen`).

В консоли Firebase:
- включите **Firestore Database** (production mode);
- включите **Authentication → Sign-in method → Anonymous**;
- вставьте содержимое `firestore.rules` в Firestore → Rules;
- зарегистрируйте веб-приложение (**Project settings → Your apps → `</>`**) —
  без этого не заработает веб-версия для гостей.

### 2. Задать ключ заведения (обязательно)

POS и оба гостевых клиента входят в Firebase анонимно, и по факту входа
отличить кассу от телефона гостя нельзя. Правила считают «персоналом»
только устройства с документом `staffDevices/{uid}`, а создать его можно,
лишь назвав ключ заведения — коллекция `meta`, документ **staffSecret**,
поле `value`:

```json
{ "value": "ваш-пароль-от-рабочих-планшетов" }
```

Без этого документа зарегистрировать планшет невозможно. При первом запуске
POS сам покажет экран «Рабочее устройство» и попросит этот ключ — вводится
один раз на планшет.

### 3. Создать первого администратора

Коллекция `employees`, документ (любой id):

```json
{ "name": "Владелец", "pinCode": "0000", "role": "admin" }
```

Дальше сотрудников и вторых админов можно добавлять уже из самого
приложения («Сотрудники» в админке).

### 4. Залить в GitHub и собрать APK

```bash
git init
git add .
git commit -m "Initial commit"
git remote add origin <ваш_репозиторий>
git push -u origin main
```

`.github/workflows/build-apk.yml` соберёт release-APK автоматически при
пуше в `main` (или вручную через Actions → Run workflow). Готовый файл — в
Actions → (последний запуск) → Artifacts. Первая сборка ~10–15 минут,
следующие быстрее за счёт кэша.

## Деплой в Firebase

Одной командой (проверяет вход, создаёт сайт хостинга при первом запуске,
выкладывает правила Firestore, индексы, хостинг и — если подключён —
Storage, затем проверяет, что сайт и страницы столов отвечают):

```bash
bash deploy.sh
```

Это то же самое, что:

```bash
firebase deploy --only firestore:rules,firestore:indexes,hosting
```

**Веб-версия для гостей и правила базы обновляются только этой командой** —
пуш в GitHub меняет код в репозитории, но не то, что реально отдаёт
`colibri-lounge.web.app`. После каждого изменения в `public/app/*` или
`firestore.rules` нужно запустить деплой заново (и убедиться, что перед
этим сделан `git pull` — иначе выложится старая версия из локальной копии).

## Логика таймера сеанса

- При старте сеанса `plannedEnd = сейчас + 90 минут`.
- «Перезабивка» полностью сбрасывает `plannedEnd` на новые 90 минут и
  увеличивает счётчик `refillCount` (история — в `refillHistory`).
- «Обновить таймер» — точечная правка (+15/+30/+60 или −15 минут) без
  сброса счётчика перезабивок.
- Таймер считается локально на каждом устройстве от `plannedEnd` из
  Firestore — все планшеты и оба гостевых клиента показывают одинаковое
  время без лишней нагрузки на базу.
- Цвета: зелёный (свободен) → синий (идёт сеанс) → оранжевый (осталось
  < 15 мин) → красный (время вышло).
- Через 35 минут после открытия/перезабивки дежурному по смене приходит
  локальное напоминание «пора проверить угли» (`session_alerts_service.dart`).

## Отчёты и аудит

- **Отчёты** (админка) и **Х-отчёт по смене** (сотрудник) — единственный
  источник финансовых цифр вместо кассового Z-отчёта: выручка, визиты,
  средний чек, перезабивки, разбивка по сотрудникам, топ позиций, скидки,
  неоплаченные закрытия, возвраты. Копирование сводки текстом в буфер.
- **Журнал кассы** (`AuditLogService`) — отдельный от отчётов, служебный:
  каждое удаление позиции, закрытие без оплаты, применённая скидка, возврат,
  правка таймера, корректировка склада — с автором и временем. Не замена
  фискальным документам, а внутренний журнал для разбора смены.
- Закрытый чек (`status == 'closed'`) нельзя изменить или удалить — это
  закреплено в `firestore.rules`, а не только в интерфейсе.

## Работа на бесплатном тарифе Firebase (Spark)

**Cloud Functions разворачивать не обязательно** — по умолчанию тумблер
«Cloud Functions подключены» в Профиле заведения выключен, и всё, что
делали бы функции, приложение делает само:

| Что делала бы функция | Кто делает без неё |
|---|---|
| Начисление кешбэка при закрытии чека | Касса на POS (`accrueBonuses`) |
| Push смене: новая бронь, вызов гостя | Локальные уведомления POS (`SessionAlertsService`) |
| Авто-неявка: снять бронь, за которой не пришли | Фоновые задания POS (`BackgroundJobsService`) |
| Поздравления с днём рождения + бонусы | Там же, раз в сутки (`BirthdayService`) |
| Push гостю: бронь подтверждена, заказ готов, бонусы | Локальные уведомления в Android-приложении гостя (`KolibriNotifications`) |
| Push гостю за час/20 минут до брони | Отложенное системное уведомление — работает даже при закрытом приложении и без сети |
| Ежедневные ИИ-сводки (брифинг, склад, отзывы, смена) | Фоновый планировщик ИИ (`ai_scheduler.dart`) на дежурном планшете |
| Обращение к LLM-шлюзу | Приложение читает ключ из `meta/aiSettings` |

Фоновые задания выполняет «дежурный» планшет — тот, что первым взял замок в
`meta/jobsLock`. Условие одно: хотя бы один планшет должен быть включён —
ночью брони разбираются утром, когда зал откроется.

Ограничение локальных уведомлений гостю: реактивные («заказ готов», «бронь
подтверждена») приходят, пока приложение живо или висит в фоне. Отложенные
(за час/20 минут до брони) планируются заранее и срабатывают в любом
случае. В веб-версии для iPhone нет и этого — там вместо push обновляющаяся
каждые 30 секунд карточка-напоминание на экране.

### Если всё-таки подключите Blaze

```bash
firebase deploy --only functions
firebase functions:secrets:set TOOKEN_API_KEY
```

И включите тумблер «Cloud Functions подключены» в Профиле заведения —
иначе гость получит по два одинаковых уведомления (от функции и от
локального механизма одновременно).

## Известные ограничения

- Нет полноценной системы ролей Firebase Auth — вход по PIN упрощён для
  небольшого заведения с доверенным персоналом; роль проверяется внутри
  приложения, а не на уровне Firebase Auth (она анонимная и общая для
  всех) — учитывайте это, кому доверяете устройства с приложением.
- По умолчанию — имитация, пока не подключён реальный провайдер: касса
  (переключается на настоящую в один шаг — см. таблицу выше), вывод кодов
  маркировки из оборота (зависит от реальной кассы), ЕГАИС (нужен физический
  УТМ), большинство банковских терминалов (см. «Фискализация и оборудование»).
- Чаевые из гостевого приложения — это запись намерения и уведомление
  персоналу, а не реальное списание денег с карты гостя.
- `cashier_layout_blueprint.dart` — визуальный референс для будущего
  редизайна экрана кассира, не рабочий экран (нигде не подключён к
  навигации, все данные в нём захардкожены).

## Если APK не открывается или зависает на загрузке

- **Приложение сразу закрывается** — почти всегда значит, что шаг
  «Подключить Firebase» не сделан или сделан с ошибкой. Приложение в такой
  ситуации не крашится, а показывает инструкцию на экране — если у вас
  старая сборка, пересоберите APK.
- **Экраны вечно крутят загрузку** — проверьте, что в консоли Firebase
  включены Firestore и Anonymous-вход, и что `firestore.rules` опубликованы
  (`bash deploy.sh`).
- **Сборка в GitHub Actions падает** — Actions → последний запуск → шаг с
  ошибкой; логи на английском, но обычно понятно, чего не хватает (чаще
  всего `flutter pub get` не может скачать зависимости или неверно указан
  `--org` в первом шаге).
- **Веб-версия не обновилась после правки кода** — пуш в GitHub не выкатывает
  сайт сам; на машине, откуда запускаете `bash deploy.sh`, сначала сделайте
  `git pull`, иначе задеплоится старая локальная копия.
